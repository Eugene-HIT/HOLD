# MPU6050 呼吸运行数据说明

## 1. 文件用途

本目录中的 [vofa_runtime.csv](captures/mpu6050_respiration/20260618_220221/vofa_runtime.csv) 是 XIAO ESP32S3 + MPU6050 单 IMU 呼吸实验在运行阶段导出的 23 列时序数据。

这份数据的用途不是医学结论输出，而是：

1. 给算法同学复盘当前固件是如何从 IMU 运动信号里判定呼吸的。
2. 观察哪些呼吸波动被接受为“有效周期”，哪些被拒绝。
3. 对比原始六轴值、呼吸载波、中间滤波量、门限量和错误码之间的关系。

## 2. 数据采样口径

### 2.1 采样阶段

这份 CSV 只包含运行阶段的数值帧，不包含校准阶段文本提示。

当前采集脚本只保留纯数值运行帧，因此：

1. 如果脚本在校准完成后启动，那么 CSV 中基本都是运行期数据。
2. 如果脚本在校准前启动，校准期文本不会写入这份 CSV，只有进入运行期后才开始出现数值行。

### 2.2 采样节拍

当前固件运行期输出节拍为 20ms 一帧，约等于 50Hz。

因此：

1. 每一行代表一次运行期状态快照。
2. 这不是“每检测到一口呼吸才输出一条”，而是持续输出的时间序列。
3. 数据中包含大量没有被最终接受为有效呼吸的中间状态，这是设计使然，不是脏数据。

### 2.3 数据分层理解

这 23 列可以分成 4 层：

1. 原始六轴层：`acc_raw_*`、`gyro_raw_*`
2. 工程信号层：`breath_carrier_g`、`breath_baseline_g`、`breath_detrended_g`、`breath_filtered_g`
3. 判定状态层：`slope_g`、`last_peak_value_g`、`last_trough_value_g`、`has_peak`、`has_trough`
4. 接收结果层：`motion_level_code`、`reject_reason_code`、`accepted_cycle_count`

## 3. 当前固件如何判定呼吸

当前固件不是直接对某一轴做过零计数，而是按下面的链路判定：

1. 校准阶段先锁定一个当前佩戴姿态下最适合观察呼吸的轴。
2. 运行阶段从该轴的加速度值中提取 `breath_carrier_g`。
3. 对 `breath_carrier_g` 做慢速基线跟踪，得到 `breath_baseline_g`。
4. 用 `breath_carrier_g - breath_baseline_g` 得到 `breath_detrended_g`。
5. 对去趋势后的信号做第一层低通，得到 `breath_filtered_g`。
6. 固件内部还有第二层更平滑的检测专用低通，但当前 CSV 没有直接导出该内部量。
7. 固件使用“检测专用低通的斜率翻转”寻找峰谷候选，并用最小摆幅门槛确认是否接受该峰谷。
8. 最后再叠加半周期时长、整周期时长、运动状态、幅度门限等条件，决定这次呼吸周期是否算作有效。

因此，这份 CSV 里：

1. 有真正被接受的呼吸周期。
2. 也有很多接近呼吸但被拒绝的候选周期。
3. 这对算法分析是有价值的，因为可以直接看到“为什么没通过”。

## 4. 23 列字段逐列说明

### 4.1 时间与主波相关字段

#### 1. `device_uptime_ms`

- 含义：设备启动后的毫秒计时。
- 单位：ms。
- 用途：作为这份 CSV 的时间轴。
- 说明：相邻两行通常约差 20ms。

#### 2. `breath_carrier_g`

- 含义：当前锁定呼吸轴上的原始加速度分量。
- 单位：g。
- 用途：这是呼吸主波最上游的工程量。
- 说明：它仍包含姿态漂移、身体轻动和呼吸起伏，不是最终判定量。

#### 3. `breath_baseline_g`

- 含义：对呼吸载波做慢速跟踪得到的基线。
- 单位：g。
- 用途：用于消除长时间姿态偏移和直流漂移。
- 说明：它应当变化较慢，不应跟随每一次呼吸快速起伏。

#### 4. `breath_detrended_g`

- 含义：`breath_carrier_g - breath_baseline_g`。
- 单位：g。
- 用途：去趋势后的呼吸相关动态量。
- 说明：比 `breath_carrier_g` 更适合观察呼吸主波起伏。

#### 5. `breath_filtered_g`

- 含义：对 `breath_detrended_g` 做第一层低通平滑后的观测量。
- 单位：g。
- 用途：这是目前最适合人工看波形的一列。
- 说明：它能较直观地反映呼吸主波，但实际峰谷判定还参考固件内部第二层检测低通，不是只看这一列。

### 4.2 判定过程相关字段

#### 6. `slope_g`

- 含义：检测专用平滑信号在当前时刻的离散斜率。
- 单位：g/采样步。
- 用途：斜率正负翻转是峰谷候选的触发基础。
- 说明：
  - 正到负翻转时，固件会考虑是否接受为峰。
  - 负到正翻转时，固件会考虑是否接受为谷。
  - 这一列不是 `breath_filtered_g` 的简单差分，而是来自固件内部更平滑的检测通道。

#### 7. `amplitude_threshold_g`

- 含义：当前有效呼吸接受所使用的最小峰谷幅值门限。
- 单位：g。
- 用途：如果峰值和谷值的差小于这个门限，则该周期会被拒绝。
- 说明：这是校准后根据个人幅度统计量计算出来的动态阈值，不是固定常数。

#### 8. `last_peak_value_g`

- 含义：最近一次已记录的峰值。
- 单位：g。
- 用途：用于后续幅度计算和峰谷顺序判断。
- 说明：不代表当前行一定刚发生峰，只是“最近一次被接受/保留的峰值状态”。

#### 9. `last_trough_value_g`

- 含义：最近一次已记录的谷值。
- 单位：g。
- 用途：用于后续幅度计算和峰谷顺序判断。
- 说明：与 `last_peak_value_g` 同理，是状态量，不是事件触发位。

### 4.3 运动门控相关字段

#### 10. `dynamic_acc_norm_g`

- 含义：加速度模长偏离 1g 的程度。
- 单位：g。
- 用途：衡量当前是否存在明显动态运动。
- 说明：值越大，说明身体或传感器的动态扰动越强。

#### 11. `gyro_norm_dps`

- 含义：三轴角速度模长。
- 单位：dps。
- 用途：配合 `dynamic_acc_norm_g` 一起做运动等级判定。
- 说明：值越大，说明当前姿态旋转或抖动更明显。

#### 12. `motion_level_code`

- 含义：当前运动等级编码。
- 编码含义：
  - `0 = still`
  - `1 = light`
  - `2 = vigorous`
- 用途：决定当前周期是否会因运动过大被拒绝。
- 注意：当前固件已放宽为 `still` 和 `light` 可接受，只有 `vigorous` 会直接触发运动拒绝。

### 4.4 接收状态与错误码字段

#### 13. `reject_reason_code`

- 含义：最近一次拒绝原因编码。
- 用途：这是理解“为什么没算进有效呼吸”的关键字段。
- 编码含义：
  - `0 = none`：当前没有新的拒绝原因，最近一次周期被接受或暂无拒绝状态。
  - `1 = warmup`：运行初期预热阶段，检测器还未开始正式判定。
  - `2 = motion_gated`：当前运动等级过高，周期因运动门控被拒绝。
  - `3 = peak_need_trough`：出现了峰，但前面缺少与之配对的谷，峰谷顺序未闭合。
  - `4 = peak_half_short`：谷到峰的半周期太短，像是毛刺或过早翻转。
  - `5 = trough_need_peak`：出现了谷，但前面缺少与之配对的峰，峰谷顺序未闭合。
  - `6 = trough_half_short`：峰到谷的半周期太短，像是毛刺或过早翻转。
  - `7 = interval_out_of_range`：整周期过短、过长，或落在接受锁定时间内。
  - `8 = amplitude_too_low`：峰谷差小于当前门限，幅度不足。

#### 14. `has_peak`

- 含义：当前状态机中是否已经持有一个有效峰状态。
- 取值：`1` 或 `0`。
- 用途：辅助判断峰谷顺序是否闭合。

#### 15. `has_trough`

- 含义：当前状态机中是否已经持有一个有效谷状态。
- 取值：`1` 或 `0`。
- 用途：辅助判断峰谷顺序是否闭合。

#### 16. `accepted_cycle_count`

- 含义：到当前行为止，已被接受为有效呼吸的周期累计数。
- 用途：判断系统到底有没有把当前这段波形真正计成呼吸。
- 说明：
  - 这是累计计数，不是每行独立标签。
  - 只有当一个完整周期通过了幅度、时长、运动门控等条件后，这一列才会增加。

#### 17. `peak_trough_balance`

- 含义：设计意图是记录 `detectedPeakCount - detectedTroughCount`，用于观察峰谷计数是否失衡。
- 用途：理论上可以辅助判断当前检测是否频繁偏向某一侧极值。
- 重要注意：
  - 当前实现里这列来自无符号整型差值，若“谷数大于峰数”，会出现很大的数值，例如 `4294967040`。
  - 这不是实际物理量，而是当前实现中的整型下溢表现。
  - 因此这列目前只能粗略参考，不能把超大值按真实平衡差直接解释。

### 4.5 原始六轴字段

#### 18. `acc_raw_x`
#### 19. `acc_raw_y`
#### 20. `acc_raw_z`

- 含义：MPU6050 三轴加速度原始寄存器值。
- 单位：LSB 原始码值。
- 当前量程换算：固件按 `16384 LSB = 1g` 解释。
- 用途：算法侧若需要重新自行滤波、重建呼吸载波，这三列是上游原始输入。

#### 21. `gyro_raw_x`
#### 22. `gyro_raw_y`
#### 23. `gyro_raw_z`

- 含义：MPU6050 三轴角速度原始寄存器值。
- 单位：LSB 原始码值。
- 当前量程换算：固件按 `131 LSB = 1 dps` 解释。
- 用途：算法侧可据此自行评估姿态转动、运动伪迹和门控策略。

## 5. 如何看这份数据

### 5.1 如果目的是看“有没有呼吸主波”

优先看：

1. `breath_carrier_g`
2. `breath_detrended_g`
3. `breath_filtered_g`

判断方式：

1. `breath_carrier_g` 里通常还能看到姿态漂移和原始波动。
2. `breath_detrended_g` 应该比上游更集中在 0 附近。
3. `breath_filtered_g` 如果存在较平滑的低频起伏，说明呼吸主波已经被提取出来了。

### 5.2 如果目的是看“为什么没被算成呼吸”

优先看：

1. `slope_g`
2. `amplitude_threshold_g`
3. `last_peak_value_g`
4. `last_trough_value_g`
5. `motion_level_code`
6. `reject_reason_code`
7. `accepted_cycle_count`

判断思路：

1. 如果 `breath_filtered_g` 有明显波，但 `accepted_cycle_count` 长时间不涨，说明问题出在“接收条件太严”，不是“主波不存在”。
2. 如果 `reject_reason_code` 经常是 `4` 或 `6`，说明半周期过短，局部毛刺仍在切碎周期。
3. 如果 `reject_reason_code` 经常是 `7`，说明整周期时间窗或接受锁定仍然偏紧。
4. 如果 `reject_reason_code` 经常是 `8`，说明峰谷幅度小于当前门限，可能是呼吸太轻、佩戴姿态不佳，或门限偏高。
5. 如果 `motion_level_code` 经常是 `2`，则很多周期会直接被运动门控拒绝。

## 6. 这份 CSV 里包含“没有被检测到的呼吸”吗

严格说，包含的是“没有被最终接受为有效呼吸的候选波动”。

更具体地说：

1. 只要进入运行期，固件每 20ms 都会输出一行状态。
2. 因此呼吸相关的连续波形、局部毛刺、接近有效但最终被拒绝的周期，都会保留在这份 CSV 里。
3. `accepted_cycle_count` 只表示“最终通过全部条件的呼吸周期累计数”。
4. 所以这份 CSV 不只是“成功样本”，而是“完整运行期过程数据”。

这对算法分析是好事，因为可以同时看到：

1. 被接受的周期长什么样。
2. 被拒绝的周期为什么没过。
3. 当前固件的门控和门限是否偏严。

## 7. 已知注意事项

### 7.1 这不是纯原始数据集

虽然现在已经包含原始六轴，但这份 CSV 仍然混合了：

1. 原始六轴值
2. 当前固件内部的工程中间量
3. 当前固件内部的状态机判定结果

因此它既可以做原始信号分析，也可以做“复盘当前规则”的分析，但不能把所有列都当独立标签真值使用。

### 7.2 `breath_filtered_g` 不是最终检测输入的完整还原

固件内部判定还经过了第二层检测低通，但这个内部量当前未直接导出。

因此：

1. `breath_filtered_g` 很适合人工看主波。
2. 但 `slope_g` 的来源不是对 `breath_filtered_g` 直接差分，而是来自内部更平滑检测通道。

### 7.3 `accepted_cycle_count` 是累计量，不是逐行标签

某一行 `accepted_cycle_count` 增加，表示在该行之前刚有一条周期通过。

因此如果要构造事件标签，不能直接把整段同一计数值的所有行都当作“这一口呼吸本身”。

### 7.4 `peak_trough_balance` 当前实现存在下溢现象

若该列出现非常大的值，例如接近 `4.29e9`，不要当作真实计数差解释。

当前更可靠的做法是：

1. 优先看 `reject_reason_code`
2. 再看 `accepted_cycle_count`
3. `peak_trough_balance` 仅作辅助参考

### 7.5 数据是否足够做算法分析

当前这份数据足够做以下工作：

1. 观察呼吸主波是否存在
2. 观察当前规则为什么拒绝周期
3. 使用原始六轴重新尝试滤波和呼吸载波构建
4. 对比“原始轴”和“当前固件工程量”之间的关系

如果后续需要更严格的算法训练数据，通常还会继续补：

1. 更明确的人工标注时间段
2. 更多体位和佩戴姿态
3. 静止、轻动、说话、转身等更多扰动场景

## 8. 建议交接说明

交给算法同学时，建议同时说明：

1. 这份 CSV 是运行期完整时序，不是只保留成功呼吸的裁剪片段。
2. 当前固件已经包含原始六轴和判定中间量，可以同时做原始分析和规则复盘。
3. 若重点关注“为什么漏检”，优先看 `reject_reason_code`、`motion_level_code`、`accepted_cycle_count`。
4. 若重点关注“能否重做算法”，优先从 `acc_raw_*`、`gyro_raw_*`、`device_uptime_ms` 开始。
