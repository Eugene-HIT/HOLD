# HOLD 对接工作反馈报告：工程迭代记录与硬件开发记录

## 摘要

本文档面向 HOLD 项目阶段性交接、科研汇报与后续工程复盘，整理 2026-05-22 至 2026-07-11 期间的主要 memory、debug、反馈、收获经验、疑难问题与可探索优化点。资料来源主要为仓库内 `log/`、`docs/`、`captures/` 与集成快照记录。

项目整体演进路线可以概括为：先完成 XIAO ESP32S3 主控与单传感器最小读数链路，再进入多传感器整机冒烟测试，随后打通 BLE 与微信小程序的用户侧控制闭环。硬件路线从 MAX30102、ICS43434、AD8232、薄膜压力、MPU6050/MPU6500、DRV2605L/LRA 与柔性热反馈等模块逐步展开，软件路线则围绕 PlatformIO 固件环境、串口诊断、VOFA 可视化、小程序 BLE 协议和数据闭环持续迭代。

当前阶段最重要的工程结论是：项目已具备多模块最小可运行能力和端到端 BLE 通信基础，但距离稳定、长期、可穿戴级产品仍有三类核心问题需要继续研究：生理信号质量与佩戴结构耦合、呼吸/心率算法的个体化稳健性、热/振动反馈的安全闭环与体感标定。

## 一、项目阶段性脉络

### 1. 起步阶段：主控与最小反馈链路

项目初期采用 XIAO ESP32S3 / ESP32S3 Plus 作为主控平台，使用 PlatformIO + Arduino 进行固件开发。早期工作重点不是复杂算法，而是确认最小硬件链路：

- 主控可正常编译、烧录、复位。
- 串口日志可稳定输出。
- 板载 LED 或外接 LED 可作为运行心跳和阶段报码。
- 后续每个传感模块均以独立 reader 或独立 env 方式接入，避免在主循环中堆叠未验证逻辑。

这一阶段形成的经验是：嵌入式原型开发必须先确认“板子活着、串口活着、日志可见”，否则后续传感器问题会与供电、串口、烧录、引脚冲突混在一起。

### 2. 单传感器 bring-up 阶段

2026-05-23 至 2026-05-25 期间，项目依次完成 MAX30102、ICS43434、AD8232 与薄膜压力模块的最小接入。

此阶段采用的通用方法是：

- 每个模块先独立建立可观察输出。
- 先证明“能读到原始数据”，再考虑算法。
- 为初始化、寄存器访问、采样窗口、串口状态保留足够诊断字段。
- 对模拟输入先做窗口统计或量化，不直接进入复杂识别。

该策略有效避免了在硬件不确定时过早引入算法复杂度。

### 3. 传感路线收敛阶段

2026-05-26 至 2026-05-28 的路线评审将项目从“所有传感器等权推进”收敛为“ECG 主路线 + PPG/OHR 备路线 + 麦克风/压力辅助 + 毫米波中长期探索”。

关键判断包括：

- MAX30102 已证明 PPG 采样与基础 BPM 能力，但它更像手指/近指夹验证，不宜直接推演为后颈或挂颈式最终方案。
- AD8232 更适合作为当前 MVP 的节律主链路，因为 ECG 对 beat-to-beat、R-R、HRV 的工程价值更直接。
- 胸带 ECG 的难点主要在结构贴合、预紧、防滑和电极材料，而不是单纯“有没有第三个参考点”。
- 毫米波可作为呼吸、体动、存在感知的辅助或中长期路线，不宜直接替代 ECG 做 HRV 主链路。

### 4. 单 IMU 呼吸识别阶段

2026-06-06 至 2026-06-09，项目围绕 MPU6050/MPU6500 进行了单 IMU 胸口呼吸检测实验。该阶段是 debug 最密集的部分之一。

工程路线经历了多次转向：

1. 原始探针：确认 I2C 地址、WHO_AM_I、accel/gyro 可读。
2. 固定阈值呼吸识别：从重力投影、峰谷检测、运动门控开始。
3. 状态机排查：通过 `detected_peaks`、`detected_troughs`、`accepted_cycles`、`last_reject` 等诊断字段定位失败原因。
4. 个体化校准：从继续调固定阈值转向“引导式校准 + 个人参数”。
5. VOFA 可视化：输出呼吸载波、基线、滤波、斜率、阈值、拒绝原因等通道，直观看清波形。
6. 二级低通与最小反转摆幅：抑制高频毛刺导致的一口多记。

该阶段的核心经验是：当真实人体佩戴带来强个体差异时，继续堆全局阈值会陷入“漏检”和“误检”的反复摆动；更稳的路线是建立个人校准和可视化诊断。

### 5. 反馈器件与整机 Demo 阶段

2026-06-11 后，项目新增 DRV2605L + LRA 独立震动环境，并在 2026-06-18 形成完整小 Demo 接线表。2026-06-28 进一步形成整机冒烟测试环境，把 IMU、PPG、压力、DRV2605L、热反馈 PWM 和 RGB 状态灯整合到同一入口。

重要策略包括：

- IMU 与 PPG 共用主 I2C：D4(GPIO5) / D5(GPIO6)。
- DRV2605L 单独使用副 I2C：D6(GPIO43) / D7(GPIO44)。
- 压力模块 AO 接 D0/A0(GPIO1)，DO 暂不接。
- RGB 使用 D8/D9/D10，并保留板载 GPIO21 作系统状态。
- 热反馈只输出 MOSFET Gate 控制 PWM，不允许 GPIO 直接驱动加热片。

整机阶段发现并修复了一个典型嵌入式问题：`Serial.printf` 参数错位导致 Guru Meditation 崩溃。该问题表现为启动阶段似乎成功，但进入运行状态打印后重启。经验是，串口日志本身也可能成为崩溃源，格式化字符串必须与参数严格一致。

### 6. BLE 与小程序闭环阶段

2026-07-11，项目重点转向“硬件已连接但小程序无数据”“呼吸反馈命令无硬件响应”“校准无可见状态变化”等端到端问题。

最终形成的 BLE 闭环包括：

- 固件广播稳定 BLE 服务 `HOLD-INTEGRATED`。
- notify characteristic 带 BLE2902/CCCD。
- command characteristic 支持 write / write-no-response。
- 固件每 500ms 发 compact JSON telemetry。
- 小程序集中管理 UUID、解析 JSON/key-value/binary fallback。
- 首页成为用户控制面，调试页保留原始包和十六进制诊断。
- 命令覆盖 `breath_start`、`breath_stop`、`calibrate_start`，并能驱动 DRV2605 与状态字段变化。

此阶段的关键收获是：BLE 问题不能只看“是否连接成功”。完整链路必须同时满足服务发现、通知订阅、包格式可解析、命令写入、固件执行与状态回传。

## 二、工程迭代记录

### 1. 平台与工程组织迭代

项目采用 PlatformIO 多环境组织方式。每个独立实验入口均通过独立 env 或独立 `src/` 子目录隔离：

- `mpu6050_xiao_esp32s3_probe`
- `mpu6050_xiao_esp32s3_respiration`
- `drv2605l_xiao_esp32s3_lra_breath`
- `xiao_esp32s3_full_smoke_test`
- MAX30102 VOFA 与 BLE 按钮链路相关环境

这种组织方式的优点是：

- 单模块验证不干扰主线固件。
- 整机联调前可以保留独立回归入口。
- 同一硬件模块在不同阶段的引脚口径可以被明确记录。
- 出问题时可以回退到更小的验证环境。

需要注意的是，独立环境过多也会带来“接线口径分裂”。因此后续应维持一份唯一的整机引脚分配表，并明确哪些引脚只是独立实验临时口径。

### 2. 串口日志与诊断口径迭代

项目早期大量依赖串口日志完成 bring-up。日志从简单心跳逐步扩展为：

- I2C 扫描和地址可见性。
- 初始化阶段 `ok/miss/reason`。
- FIFO 指针、寄存器回读、错误计数。
- 传感器窗口统计。
- 呼吸状态机拒绝原因。
- VOFA 纯数值流。
- 整机状态单行汇总。
- BLE telemetry JSON。

这一过程表明，嵌入式项目中的“debug 输出”本身是工程资产，而不是临时噪声。它帮助团队从“感觉没反应”转向“知道卡在哪一层”。

### 3. 小程序工程迭代

小程序侧经历了从调试页、页面壳、首页控制面到 BLE 协议统一的过程。关键迭代点包括：

- 清理 sitemap 提示，避免开发者工具噪音干扰判断。
- 将首页定位为真实用户控制面。
- 将 debug 页定位为协议诊断面。
- 建立 `web/utils/ble-protocol.js`，统一 UUID、解析、字段归一化和中文标签。
- 支持原始通知包、解析后 metrics、连接状态、校准状态、呼吸引导状态展示。

经验是：用户界面和调试界面需要分层。把所有诊断内容塞进用户首页，会降低交互清晰度；但完全隐藏原始包，又会降低联调效率。

### 4. 数据导出与可视化迭代

项目在 IMU 呼吸和 MAX30102 阶段均使用 VOFA 或 CSV 作为关键观察工具：

- MPU6050 呼吸输出 23 列原始轴、滤波信号、状态机字段。
- MAX30102 手指/胸口实验输出 Red/IR、接触、滤波、幅值等字段。
- VOFA 用于确认“是否有主波”“毛刺在哪”“阈值是否与波形同量级”。

这说明当前项目已经从纯串口文本调试转向半结构化实验数据采集。后续若要偏科研，应进一步统一数据格式、实验标签、佩戴位点、动作条件与样本编号。

## 三、硬件开发记录

### 1. XIAO ESP32S3 主控

主控承担多传感器采样、反馈控制、BLE 广播与命令处理。已验证内容包括：

- PlatformIO 编译与烧录。
- USB 串口监视。
- 板载 LED 心跳。
- 多 I2C 与 ADC 混合使用。
- BLE 服务、通知与命令通道。

疑难点：

- 串口工具占用 COM 口会导致上传失败。
- ESP32S3 启动脚和板载 LED 逻辑需要避免误用。
- 整机联调时，日志格式错误可直接导致运行期崩溃。

### 2. MAX30102 PPG

开发目标从“能读到 Red/IR 原始值”逐步推进到“简单 BPM 与接触质量判断”。

主要成果：

- I2C 地址 0x57 和 Part ID 校验。
- FIFO 指针、配置寄存器、slot 配置与 rollover 诊断。
- 连续 Red/IR 原始样本输出。
- 基于 IR 的轻量心率估计。
- 窗口均值触点判断与 PBA 风格峰值检测。

主要 debug 记录：

- 初期出现 `part-id-read-failed`、`part_id=0x0`，需要 I2C 扫描和周期重扫。
- 后续出现 `reason=ok` 但 `wr_ptr=0 | rd_ptr=0 | avail=0`，说明通信成功但 FIFO 未产样本。
- 加入 slot 配置与关键寄存器回读后，FIFO 开始累计样本。
- `beats=0` 更像算法阈值和状态机问题，而不是硬件完全失效。
- 2Hz 串口输出只是显示频率，不等于传感器采样频率。

经验：

- PPG 调试不能只看设备识别，要同时看 FIFO 是否滚动、配置是否回读成功、接触均值是否稳定。
- 单点接触判断不可靠，窗口均值更稳。
- 从手指到胸口或其他位点时，PPG 的光机结构和贴合压力会显著改变信号质量。

### 3. ICS43434 数字麦克风

开发目标为 I2S 最小读取链路。

主要成果：

- 新增 I2S 引脚、采样率、DMA、批处理配置。
- 每 10ms 尝试读取样本批次，每 500ms 输出窗口统计。
- 输出 `min/max/p2p/mean` 等能量级字段。
- 实机确认 `seq`、`p2p`、`mean` 持续变化。

疑难点：

- 曾出现 `main.cpp` 被旧版本逻辑覆盖导致看不到麦克风信息。
- 第三方串口工具可能出现显示会话异常，PlatformIO 监视器确认固件实际输出。
- 声道选择、I2S 引脚丝印差异会造成数值异常弱或空读。

经验：

- 音频模块第一阶段只证明“有样本、有能量变化”即可，不应提前扩展声源识别。
- 若后续要做声音事件，应单独规划窗口、阈值、频域特征和隐私边界。

### 4. AD8232 ECG

开发目标为 OUTPUT 模拟量到 ADC 的最小链路，并为后续 R 峰和 HRV 做准备。

主要成果：

- OUTPUT 接 D1/A1/GPIO2。
- ADC 约 250Hz 轮询。
- 串口输出原始值和窗口统计。
- 支持 VOFA 单列原始 ADC 输出。
- 实机确认 raw/mean/max/p2p 持续变化。

疑难点：

- 当前读到变化不等于高质量 ECG。
- 多次出现 `min=0`，可能对应未贴附、接触不良、偏置不稳或噪声较大。
- LO+ / LO- 尚未纳入导联脱落判断。

经验：

- ECG 主线的真正难点在佩戴结构、电极接触和运动伪差。
- 凝胶电极适合作为研发基准件，不宜直接视为最终消费产品方案。
- 两电极适合产品化胸带，三电极更适合研发阶段稳定前端。

### 5. 薄膜压力模块

开发目标为 AO 模拟量读取并映射为 0-10 相对等级。

主要成果：

- AO 接 D0/A0/GPIO1。
- 启动时采集静置基线。
- 少量 ADC 采样平均后输出相对压力等级。
- 串口输出 `[pressure] N`，便于肉眼判断。

疑难点：

- 实机初期多为 `[pressure] 0`，更可能是未按压或模块未接入 AO，不代表代码失效。
- 不同模块 AO 动态范围可能不同，需要保留最小量程参数。

经验：

- 压力模块本阶段只使用 AO；DO 是比较器二值输出，不适合表达连续压力。
- 启动基线采集能避免空载偏置直接映射为非零等级。

### 6. MPU6050 / MPU6500 IMU

开发目标包括原始姿态/运动读取、呼吸节律估计和运动门控。

主要成果：

- I2C 探针确认模块在线。
- 兼容 MPU6050、MPU6500、MPU9250/9255 常见 WHO_AM_I。
- 输出加速度、角速度、pitch/roll、运动等级。
- 建立单 IMU 呼吸状态机和个体化校准。
- 接入 VOFA 调试流。

疑难点：

- 初期呼吸字段长期 `n/a`，原因不是完全无数据，而是重力投影和阈值过保守。
- 峰值计数快速增长而谷值不增长，说明状态机被高频扰动刷新。
- 时间窗过紧会让有效周期归零，过松又会导致一口多记。
- 累计平均周期显示会让用户误以为板载时钟不准。
- 校准阶段若只记录原始轴范围，会被姿态漂移拉高阈值。

经验：

- 呼吸识别必须区分“有没有主波”和“状态机是否正确接受主波”。
- 固定阈值难以覆盖不同佩戴方式和个体呼吸差异。
- 需要把运行期判定量与校准期学习量保持同一量纲。
- VOFA 曲线对定位高频毛刺、阈值失真和过早触发非常关键。

### 7. DRV2605L + LRA 震动反馈

开发目标为深呼吸式触觉引导。

主要成果：

- 独立 env 初始化 DRV2605L。
- 使用 LRA + RTP 实时播放模式。
- 输出吸气/呼气强到弱包络。
- 副 I2C D6/D7 独立于传感主总线。
- BLE 阶段命令可驱动 DRV2605 状态变化。

疑难点：

- 尚未根据具体 LRA 型号设置 rated voltage、overdrive clamp 和 auto-calibration。
- 体感强度、颗粒感、吸呼分辨度仍需人体确认。
- 震动可能通过机械耦合影响 PPG 或 IMU 信号。

经验：

- 触觉反馈应先独立验证体感，不要一开始并入传感状态机。
- DRV2605L 使用 RTP 更适合长呼吸节律包络，内置 ROM 效果更适合短脉冲。

### 8. 柔性热反馈

开发目标为热反馈控制脚与安全边界定义。

主要成果：

- 文档中补充柔性电加热片/发热膜。
- 整机冒烟环境中加入热反馈 PWM 控制脚。
- 上电先拉低，延迟 5 秒后再输出 80% PWM，便于观察启动阶段。
- 明确必须使用逻辑级 N-MOSFET 控制外部电源。

疑难点：

- 当前缺少加热片额定参数。
- 尚未建立温度采样、限温保护、安全时长和热舒适度闭环。

经验：

- GPIO 不能直接驱动加热片。
- 开环 PWM 只能作为控制脚验证，不宜作为长期功能。

### 9. RGB 状态灯

开发目标为整机阶段可视化状态反馈。

主要成果：

- RGB 共阴极接 D8/D9/D10。
- 启动阶段加入 R/G/B 单色自检。
- 板载 GPIO21 保留为系统状态灯。

疑难点：

- 外接 RGB 与板载 LED 的有效电平逻辑不同。
- 若蓝色不亮，应优先查 GPIO9、限流电阻、极性和共阴极接法。

经验：

- RGB 是低成本但高价值的现场诊断工具，可用于无串口场景下判断固件阶段。

## 四、关键疑难点与排查过程

### 1. MAX30102：设备识别、FIFO 与算法三层问题混杂

现象包括 Part ID 失败、FIFO 不滚动、`beats=0`、BPM 显示停滞。

排查路径：

1. 用 I2C 扫描确认地址是否可见。
2. 用 Part ID 与关键寄存器回读确认通信层是否稳定。
3. 用 FIFO 指针确认是否真的有样本。
4. 用 Red/IR 原始值确认光学通道是否变化。
5. 用窗口均值确认接触质量。
6. 最后才调峰值检测和 BPM 状态机。

收获：

- 同一个“没有心率”的表现可能来自硬件、寄存器配置、FIFO、接触、算法任一层。
- 必须保留跨层诊断字段，否则容易误判。

### 2. IMU 呼吸：固定阈值陷入反复调参

现象包括正常呼吸难触发、剧烈运动反而触发、深呼吸一口多记、有效周期漂移。

排查路径：

1. 增加峰/谷计数和拒绝原因。
2. 区分半周期过短、整周期不合格、振幅太低和运动门控。
3. 修复极值时间反复刷新的状态机问题。
4. 拆分最近一次周期和历史平均周期显示。
5. 引入个体化校准。
6. 接入 VOFA 观察真实波形和毛刺。
7. 加入最小反转摆幅和检测专用二级低通。

收获：

- 人体佩戴下的呼吸信号不是理想正弦。
- 阈值不能只根据想象调整，必须回到曲线和拒绝分布。
- 个体化校准不是额外复杂度，而是减少全局阈值反复拉扯的必要步骤。

### 3. BLE：连接成功不等于协议闭环成功

现象包括小程序已连接但无数据、收到无法解析通知、按钮命令无硬件响应、校准无可见变化。

排查路径：

1. 确认固件广播稳定 service。
2. 确认 notify characteristic 带 BLE2902/CCCD。
3. 确认小程序订阅通知成功。
4. 统一固件上报格式为 JSON telemetry。
5. 统一小程序协议解析。
6. 增加 command characteristic，并让固件把命令转为 DRV2605 与状态字段变化。

收获：

- BLE 链路至少包含发现、订阅、解析、写入、执行、回传六个环节。
- 首页和 debug 页应共用协议层，避免两个页面各自实现导致行为不一致。

### 4. 整机冒烟：启动成功后运行期崩溃

现象为 setup 阶段完成、加热使能后不久自动重启。

排查结论：

- 不是单纯加热负载或 I2C 卡死，而是一处整机状态行 `Serial.printf` 参数错位触发 Guru Meditation。

收获：

- 串口诊断代码也属于运行逻辑，必须编译和实机验证。
- 冒烟测试应包含 boot 分段日志，帮助区分初始化失败和运行期崩溃。

### 5. 热反馈：控制脚验证与安全功能不能混为一谈

现象与边界：

- 整机工程目前只验证 PWM 控制脚。
- 尚未拿到加热片额定参数。
- 无温度闭环、限温、超时和热舒适度评价。

收获：

- 热反馈必须作为高风险反馈通道处理。
- 没有闭环前，不应把 80% PWM 理解为可长期使用的功能参数。

## 五、阶段性反馈与科研化归纳

### 1. 工程方法论反馈

本项目最有效的方法不是一次性搭完整系统，而是“最小链路 -> 诊断可见 -> 单模块收口 -> 整机冒烟 -> 端到端闭环”。该方法尤其适用于多传感器可穿戴原型，因为硬件、佩戴、算法和交互之间高度耦合。

科研化表达可归纳为：

- 对每个传感器建立独立观测通道，降低变量耦合。
- 以原始数据可获取性作为第一验收标准。
- 以可解释中间变量作为算法迭代依据。
- 以整机冒烟测试验证模块间的供电、总线和状态交互。
- 以 BLE 与小程序闭环验证系统级可用性。

### 2. 硬件路线反馈

当前硬件路线已覆盖生理、行为、反馈三层：

- 生理层：ECG、PPG、IMU 呼吸。
- 行为/环境辅助层：压力、麦克风、运动等级。
- 反馈层：LRA 震动、RGB、热反馈。

但下一阶段应避免继续横向扩传感器数量，优先提升现有主链路质量。建议按优先级聚焦：

1. AD8232 ECG：R 峰、R-R、短窗 HRV、导联稳定性。
2. IMU 呼吸：个体化校准、有效周期、叹气/深呼吸事件。
3. DRV2605L：体感包络、强度标定、反馈与检测互扰。
4. BLE 小程序：稳定控制、状态回传、数据记录。
5. 热反馈：只有在温控安全方案明确后再进入长期功能。

### 3. 算法路线反馈

当前算法迭代已经显示，简单阈值法可用于最小验证，但难以支撑稳定人体佩戴。

建议后续算法分层：

- 信号质量层：接触、运动、噪声、漂移、饱和。
- 基础事件层：心跳、呼吸峰谷、压力变化、动作强度。
- 个体化参数层：用户基线、呼吸节律、ECG 波形幅度、佩戴位点。
- 状态融合层：焦虑相关趋势或引导触发，不直接承诺医学诊断。

### 4. 交互与产品路线反馈

小程序已从调试工具转向用户控制面，但仍处于工程验证阶段。后续建议：

- 首页只放用户真正需要的控制和状态。
- debug 页保留原始 BLE 包、hex、协议字段和错误码。
- 将校准过程做成明确步骤，而不是仅依赖串口提示。
- 将呼吸引导、震动反馈和校准结果联动展示。

## 六、可探索优化点

### 1. 数据与实验规范

建议建立统一实验数据模板：

- 受试者编号或匿名代号。
- 佩戴位点。
- 传感器型号和接线版本。
- 固件 env 和 commit。
- 工况标签：静坐、说话、走动、深呼吸、叹气、按压、反馈开启。
- 原始数据字段说明。
- 观察结论和异常标记。

这将把当前“工程日志”进一步升级为可复现实验记录。

### 2. ECG 主链路

可探索方向：

- 加入 LO+ / LO- 导联脱落状态。
- 输出原始 ECG 与轻滤波 ECG 双通道。
- 实现 R 峰检测、BPM、R-R 间期。
- 比较横向胸带布局和类 Lead II 斜向布局。
- 对比凝胶电极、导电织物、金属干电极、导电硅胶。
- 记录静坐、说话、走动、深呼吸下的波形可用性。

### 3. PPG/OHR 备路线

可探索方向：

- 保留 MAX30102 作为 PPG 数据能力验证和对照。
- 不再将 MAX30102 后颈化作为主路线。
- 若重启光学路线，优先明确耳部、太阳穴、上臂或腕部位点。
- 评估绿光主导或集成多波长 wearable OHR 模组。
- 把遮光、压紧、air gap、串扰纳入结构设计，而不是只调固件。

### 4. IMU 呼吸

可探索方向：

- 将个人 profile 持久化到 Flash/NVS。
- 增加轻微活动干扰段校准。
- 继续保留 VOFA 输出，用曲线验证二级低通与反转摆幅。
- 在统计阈值之上尝试逻辑回归或小决策树。
- 与毫米波呼吸或 ECG 呼吸性调制做可信度互补。

### 5. 反馈闭环

可探索方向：

- DRV2605L 针对具体 LRA 做 auto-calibration。
- 建立触感主观评分表：强度、节律、舒适度、可分辨度、打扰程度。
- 研究震动对 IMU/PPG 的机械干扰。
- 热反馈加入温度传感、限温、超时、软启动和异常断开。

### 6. BLE 与小程序

可探索方向：

- 将 telemetry schema 固化成版本化协议。
- 为每条命令加入 ack、错误码和状态机。
- 小程序侧记录连接、订阅、命令、通知的时间线。
- 支持导出 CSV/JSON 实验包。
- 手机端完成校准引导，减少对串口的依赖。

| BLE 手机端完整实机验证 | PC BLE 已验证，小程序手机端仍需持续测 | 高 |
| LRA 体感强度与舒适度 | 命令路径已通，主观体验未定量 | 中 |

## 八、交接建议

下一位对接工程师或研究成员建议按以下顺序接手：

1. 先阅读 `docs/2026-06-18-完整小demo接线表.md`，按唯一整机接线口径搭硬件。
2. 烧录 `xiao_esp32s3_full_smoke_test`，确认 IMU、PPG、压力、DRV2605L、RGB、热反馈控制脚的 boot 与 runtime 状态。
3. 用 BLE 小程序连接 `HOLD-INTEGRATED`，验证 telemetry、`calibrate_start`、`breath_start`、`breath_stop`。
4. 若目标是生理指标，优先回到 AD8232 ECG 独立链路，补 R 峰/R-R，而不是继续扩新传感器。
5. 若目标是呼吸引导，优先继续 IMU 个体化校准和 LRA 体感标定。
6. 热反馈只允许在安全闭环设计完成后进入长时间人体测试。

## 九、结论

HOLD 项目当前已从“单点硬件试验”推进到“多传感器整机 + BLE 小程序控制”的阶段。项目的主要价值不只在于某个传感器已经能读数，而在于形成了一套较完整的原型研究方法：单模块最小验证、详细串口诊断、可视化数据流、阶段性路线评审、整机冒烟测试和端到端交互闭环。

后续最值得投入的方向不是继续增加模块数量，而是把主链路做深：以 ECG 或个体化 IMU 呼吸为核心，建立可重复采集、可解释诊断、可量化反馈和可安全佩戴的验证体系。只有当信号质量、佩戴结构、反馈安全和数据记录四件事同时闭环后，项目才真正从工程 Demo 进入可研究、可评估、可迭代的科研原型阶段。
