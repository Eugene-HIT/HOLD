# 小程序直连硬件开发文档

## 头部信息
- 创建时间：2026-06-17
- 最后更新时间：2026-06-17
- 文档类型：开发前要求文档 / 传输链路重构规划文档
- 所属模块：微信小程序 / BLE 通信 / 云函数中转 / 云存储 / 大模型接入
- 文档用途：基于 ref 目录旧项目中的安卓 App、小程序、云函数链路，规划一套“硬件直接与微信小程序通信，绕过安卓 App”的新方案，并明确可复用项、必改项、边界条件与阶段实施要求
- 输入：
  - 旧小程序工程 ref/miniapp_for_Gulu
  - 旧安卓工程 ref/MyApplication
  - 当前硬件项目目标：上传呼吸、心率等数据，并保留后续大模型分析入口
- 输出：一份适用于新项目落地的小程序端技术方案文档

## 1. 文档目的
本文件用于回答三个问题：

1. 旧项目的哪些链路可以直接沿用。
2. 旧项目里哪些职责原本由安卓 App 承担，迁移到“小程序直连硬件”后必须重构。
3. 新项目首版应该采用什么技术栈、数据流、云函数边界和开发阶段顺序。

本文件强调以下原则：

- 不允许把旧安卓方案原样平移为小程序方案。
- 不允许默认认为小程序可以无约束替代安卓后台能力。
- 不允许把大模型密钥继续放在前端。
- 不允许走“先随便打通再说”的最小实现捷径来回避链路设计。

## 2. 已核对的旧项目事实

### 2.1 旧小程序的实际职责
基于 ref/miniapp_for_Gulu 中代码，旧小程序当前主要职责不是硬件直连，而是云端展示与指令上传。

已确认行为：

1. 小程序初始化了微信云开发。
   - 证据：ref/miniapp_for_Gulu/app.js 中调用 wx.cloud.init。

2. 小程序主页通过轮询云数据库读取设备状态。
   - 证据：ref/miniapp_for_Gulu/pages/index/index.js 中定时调用 fetchCloudData。
   - 读取集合：device_status。

3. 小程序会把用户录音上传到云存储，并在 app_commands 集合中登记为未读指令。
   - 证据：ref/miniapp_for_Gulu/pages/index/index.js 中 uploadCommandAudio。

4. 小程序会把云存储里的语音拉成临时链接并在手机本地播放。
   - 证据：ref/miniapp_for_Gulu/pages/index/index.js 中 playAudio 与 wx.cloud.getTempFileURL。

5. 工程里虽然存在 mqtt.min.js，但当前检索结果没有发现业务代码实际引用该 MQTT 库。
   - 结论：旧小程序主链路并不依赖 MQTT 落地。

### 2.2 旧云函数的实际职责
基于 ref/miniapp_for_Gulu/cloudfunctions 中代码，旧云函数主要承担两类职责：

1. update_gulu_status
   - 为设备侧申请云存储直传凭证。
   - 将设备上传后的 fileID 登记到 device_status 集合。
   - 兼容文本、图片、音频三类状态入库。

2. pull_command
   - 从 app_commands 集合中取最早一条未读语音命令。
   - 标记该命令为已读。
   - 把 cloud:// 文件地址转换为临时 https 下载地址后返回。

结论：
- 旧云函数与云数据库/云存储模型有较强复用价值。
- 这部分可以继续作为新方案的云端骨架。

### 2.3 旧安卓 App 的实际职责
基于 ref/MyApplication 中主工程代码，旧安卓不是简单客户端，而是整个系统的核心桥接层。

已确认职责：

1. BLE 中心设备
   - 扫描、连接 ESP32 硬件。
   - 订阅多个 GATT Characteristic。
   - 向设备回写音频与命令。

2. 本地音频采集与播放
   - 采集手机麦克风音频。
   - 本地播放来自设备或云端的 PCM/WAV 音频。

3. 设备媒体上云
   - 调用云函数申请上传凭证。
   - 直传音频/图像到云存储。
   - 调用 saveUploadedFile 进行数据库登记。

4. 轮询云端用户指令
   - 定时调用 pull_command。
   - 下载语音命令。
   - 手机本地播放，并转发给硬件扬声器链路。

5. 大模型调用
   - 直接从 App 调用 Kimi / 智谱 Chat 接口。
   - 直接建立阿里 DashScope WebSocket 进行语音能力处理。
   - 直接调用火山 TTS 接口。

结论：
- 旧安卓同时承担了“BLE 网关 + AI 网关 + 云网关 + 音频中控”。
- 新项目如果绕过安卓，就必须显式拆分这些职责，不能只把 UI 换成小程序。

## 3. 新项目目标定义

### 3.1 核心目标
新项目需要实现：

1. 硬件与微信小程序直接通信。
2. 小程序可展示硬件实时或准实时状态。
3. 呼吸、心率等关键数据可上云保存。
4. 云端保留后续大模型分析与报告生成入口。
5. 去掉安卓 App 作为必须中间层。

### 3.2 首版建议目标
首版建议目标收敛为：

1. 小程序完成 BLE 扫描、连接、订阅、写入。
2. 硬件按结构化数据包上报呼吸、心率、状态事件。
3. 小程序将摘要数据写入云数据库，将必要原始片段或报告写入云存储。
4. 云函数负责：
   - 设备数据标准化入库
   - 用户会话记录整理
   - 后续大模型分析任务触发
5. 首版不要求在小程序内复刻旧安卓的全部“实时语音双工交互”。

原因：
- 小程序虽然支持 BLE，但前后台行为、连接保持、长时间实时音频流能力都不应默认等同安卓原生 App。
- 当前新硬件项目重点是呼吸/心率等生理数据，不是完整语音陪伴主链路。

补充说明：
- 若当前阶段仅需“先打通链路”，请优先执行同目录下的 [小程序首版按钮链路打通开发要求.md](log/dev/2026-06-17/miniapp/direct-ble-plan/小程序首版按钮链路打通开发要求.md)。
- 该文档面向“只有 XIAO ESP32S3 Plus 开发板、暂时没有既有传感模块”的最小闭环验证。

## 4. 关键事实与边界条件

### 4.1 已确认可行项
根据微信官方文档：

1. 小程序支持 BLE 设备连接。
   - 已核对官方 API：wx.createBLEConnection。

2. 小程序支持 BLE 适配器与后续 GATT 操作体系。
   - 虽本次抓取 openBluetoothAdapter 页面失败，但 createBLEConnection 官方文档明确依赖蓝牙适配器初始化，说明 BLE 主链路能力存在。

3. 小程序云开发支持数据库、云存储、云函数。
   - 已核对微信云开发开发指引。

结论：
- “硬件直连小程序 + 云开发后端”作为总体路线是成立的。

### 4.2 不能直接照搬的旧能力
以下能力不应直接假定能被小程序无缝替代：

1. 安卓式常驻后台 BLE 网关。
2. 安卓式长时间高稳定双向语音流桥接。
3. 在前端持有大模型/语音服务密钥直接调用第三方 API。
4. 像安卓一样自由管理本地音频缓冲、线程和持续播放链路。

因此新方案必须把旧安卓中的职责重新切分为：

- 小程序端实时交互职责
- 云函数端安全代理职责
- 硬件端协议适配职责

### 4.3 当前无法可靠确认项
以下点在当前工程与已核对资料范围内无法可靠确认，必须保留为待验证项：

1. 新硬件是否需要持续高频原始波形上传，还是只上传算法摘要。
2. 小程序前台驻留时，对目标采样频率和包长的 BLE 吞吐是否足够。
3. 是否要在首版加入“小程序向硬件推送语音播放”能力。
4. 后续大模型分析是实时在线返回，还是离线异步生成报告。

## 5. 新旧架构对比

### 5.1 旧架构
旧架构可概括为：

硬件 -> 安卓 App -> 云函数/云存储/数据库 -> 小程序展示

用户语音命令链路为：

小程序录音 -> 云存储 -> app_commands -> 安卓轮询 -> 安卓播放/转发给硬件

### 5.2 新架构
新架构建议改为：

硬件 <-> 小程序 BLE

小程序 -> 云函数 -> 数据库/云存储 -> 报告/分析结果 -> 小程序

如果后续引入 AI：

小程序 -> 云函数 AI 代理 -> 第三方大模型 / TTS 服务 -> 结果回云端 -> 小程序读取

### 5.3 架构变化的本质
本次重构的本质不是“把安卓页面换成小程序页面”，而是：

1. 设备通信层从安卓 BLE 网关改成小程序 BLE 网关。
2. AI 调用层从前端直调第三方改成云函数代理。
3. 数据展示层保留小程序现有的云端拉取模式。
4. 数据模型尽量复用旧 cloud database / cloud storage 思路。

## 6. 推荐技术栈

### 6.1 小程序端
- 原生微信小程序
- JavaScript
- 微信 BLE API
- 微信云开发 SDK

首版不建议引入复杂前端框架，原因：
- 当前主要难点在 BLE 协议与云端链路，不在前端组件规模。
- 原生小程序 API 对 BLE 能力最直接，调试路径最短。

### 6.2 云端
- 微信云开发
- 云数据库
- 云存储
- 云函数 Node.js

### 6.3 AI 与扩展服务
建议统一收敛到云函数代理层，不再由前端直接持有密钥。

可接入类型：
- 大模型文本分析
- TTS 生成
- 语音识别
- 报告摘要生成

### 6.4 硬件侧
硬件建议采用 BLE GATT 自定义服务，按“配置明确、数据分流、事件独立”的方式设计。

## 7. 推荐数据流设计

### 7.1 被动监测数据流
1. 小程序连接硬件 BLE。
2. 订阅“生理摘要特征”通知特征。
3. 硬件周期上报：
   - 呼吸频率
   - 心率
   - 佩戴状态
   - 信号质量
   - 事件标志
4. 小程序本地展示最新值。
5. 小程序按节流策略写入云函数。
6. 云函数清洗后写入数据库。

### 7.2 主动检测数据流
1. 用户在小程序端点击“开始主动检测”或硬件侧按压触发。
2. 小程序向硬件写入命令。
3. 硬件进入主动检测会话。
4. 硬件上报会话状态与最终结果。
5. 小程序将结果提交云函数入库。
6. 云函数可触发报告生成。

### 7.3 AI 分析数据流
1. 小程序请求生成日报/一次检测分析。
2. 云函数读取数据库中的摘要数据与必要上下文。
3. 云函数调用第三方大模型。
4. 生成结构化分析结果。
5. 写回报告集合或云存储。
6. 小程序拉取展示。

## 8. 推荐云端数据模型

### 8.1 device_sessions
用于记录一次设备连接会话。

建议字段：
- session_id
- user_id
- device_id
- started_at
- ended_at
- source: miniapp
- firmware_version
- app_version

### 8.2 vital_stream_summary
用于保存节流后的生理摘要。

建议字段：
- session_id
- timestamp
- respiration_bpm
- heart_rate_bpm
- hrv_score_optional
- wear_state
- signal_quality
- alert_flags

### 8.3 active_measurements
用于保存主动检测结果。

建议字段：
- measurement_id
- session_id
- trigger_source
- started_at
- ended_at
- measurement_type
- result_summary
- raw_file_id_optional
- report_status

### 8.4 reports
用于保存 AI 或规则引擎生成的报告。

建议字段：
- report_id
- measurement_id_or_session_id
- report_type
- generated_at
- report_text
- report_json
- llm_provider
- llm_version

### 8.5 miniapp_commands
若后续仍保留从小程序向硬件发命令的云端留痕，可保留类似旧 app_commands 的集合，但不建议首版依赖轮询执行。

## 9. 推荐 BLE 协议拆分

### 9.1 服务划分建议
建议至少保留一个主服务，并分成多个特征：

1. status characteristic
   - 设备状态
   - 电量
   - 连接模式

2. vital summary notify characteristic
   - 呼吸率
   - 心率
   - 信号质量
   - 告警状态

3. control write characteristic
   - 开始主动检测
   - 停止主动检测
   - 清空会话
   - 获取版本

4. session result notify characteristic
   - 主动检测结果
   - 会话完成事件

### 9.2 首版不建议内容
首版不建议通过 BLE 持续传输：

1. 大段原始 PCM 音频
2. 大尺寸图像
3. 高频未压缩原始波形长流

原因：
- 新项目当前核心不是复刻旧安卓语音陪伴系统。
- 首版应优先保证呼吸/心率链路稳定、数据模型闭环清晰。

## 10. 云函数职责拆分建议

### 10.1 ingest_device_summary
职责：
- 接收小程序上送的摘要数据
- 校验 user_id、device_id、session_id
- 做字段标准化
- 写入 vital_stream_summary

### 10.2 save_active_measurement
职责：
- 接收主动检测结果
- 保存结果摘要
- 关联原始文件
- 创建待生成报告任务

### 10.3 generate_report
职责：
- 读取目标检测数据
- 调用规则引擎或大模型
- 生成报告
- 写入 reports

### 10.4 llm_proxy
职责：
- 作为统一 AI 出口
- 安全保存第三方密钥
- 控制模型调用频率与日志

### 10.5 upload_artifact_token
若后续仍有文件直传需求，可保留“申请云存储上传凭证”的云函数，与旧 update_gulu_status 里的 getUploadMetadata 思路一致。

## 12. 安全与合规要求

### 12.1 必须执行
1. 大模型、TTS、ASR 等第三方密钥不得放在小程序前端。
2. 云函数必须校验用户身份与最小必要参数。
3. 数据库写入要区分 user_id 与 device_id。
4. 报告输出不得伪装成医学诊断结论。

### 12.2 不建议保留的旧做法
旧安卓工程中存在前端直接持有第三方密钥的实现痕迹，新项目不应沿用。

## 13. 分阶段开发计划

### 阶段 1：链路打通
目标：
- 小程序 BLE 扫描、连接、订阅成功
- 硬件可上报呼吸率/心率摘要
- 小程序可显示数据

验收标准：
- 连接稳定
- 可持续接收摘要数据
- 断开重连流程可用

### 阶段 2：云端闭环
目标：
- 小程序将摘要数据写入云函数
- 云函数完成入库
- 小程序可查看历史记录

验收标准：
- 数据结构稳定
- 历史数据查询正常

### 阶段 3：主动检测闭环
目标：
- 小程序可发起主动检测
- 硬件完成会话
- 结果写云端并展示

验收标准：
- 主动检测流程端到端可复现

### 阶段 4：报告与 AI 接入
目标：
- 云函数代理大模型
- 生成结构化分析报告
- 小程序展示报告

验收标准：
- 不暴露密钥
- 报告生成链路完整

## 14. 待确认事项
1. 硬件首版上报的是摘要值还是短窗原始序列。
2. 主动检测触发以小程序按钮为主，还是硬件压感触发为主。
3. 是否保留“设备播报语音”能力作为首版需求。
4. AI 报告是实时生成还是异步生成。
5. 历史数据保留周期与云存储成本上限。

## 16. 结论
本次分析后的推荐结论是：

1. 继续沿用旧项目的云开发总体思路是合理的。
2. 可复用的是：云数据库、云存储、云函数职责模型、小程序展示思路。
3. 不能直接复用的是：安卓承担的 BLE、音频中控、AI 直调职责。
4. 新项目首版应聚焦“BLE 摘要数据直连 + 云端入库 + 报告留口”，而不是先复刻完整语音双工系统。
