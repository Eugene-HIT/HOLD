# 小程序首版按钮链路打通开发要求

## 头部信息
- 创建时间：2026-06-17
- 最后更新时间：2026-06-17
- 文档类型：开发前要求文档 / 首版 MVP 链路打通要求
- 所属模块：XIAO ESP32S3 Plus / 微信小程序 / BLE / 云函数 / 云数据库 / 云存储 / 大模型代理
- 文档用途：指导当前阶段用一块 XIAO ESP32S3 Plus 开发板完成“按钮触发 -> 小程序显示 -> 云端入库与存储 -> 成功调用大模型”的最小闭环
- 输入：
  - 一块 XIAO ESP32S3 Plus 开发板
  - 当前 PlatformIO 根工程
  - 新建微信小程序工程
  - 微信云开发环境
- 输出：
  - 一份可执行的最小链路打通要求
  - 一套明确的 BLE、云函数、数据库、云存储、LLM 验证边界

## 1. 文档目的
本文件只服务于今天的目标：

1. 开发板按一次按钮。
2. 小程序通过 BLE 收到事件。
3. 小程序界面明确显示“收到一次按钮事件”。
4. 小程序把这次事件送到云端。
5. 云函数完成数据库写入与云存储留痕。
6. 云函数成功代理调用一次大模型。
7. 小程序拿到大模型返回结果并显示出来。

这意味着今天要验证的不是完整产品，而是 5 条链路是否都通：

- 蓝牙链路
- 小程序前端链路
- 云函数链路
- 云存储链路
- 大模型链路

## 2. 当前阶段约束

### 2.1 已知约束
当前只有一块 XIAO ESP32S3 Plus 开发板，没有此前已经做好的传感模块。

因此今天的硬件侧目标不能写成：
- 呼吸数据上传
- 心率数据上传
- 多传感器融合

今天的硬件侧目标必须收敛为：
- 用一个按钮事件模拟“硬件产生了一条上报事件”

### 2.2 今日允许的临时做法
允许把板载按钮当作临时输入源，但必须明确它只是验证链路，不是最终产品输入设计。

根据 Seeed 官方资料，XIAO ESP32S3 / Plus 具有 Boot 按钮，且 Boot 对应 GPIO0，为启动绑带脚。

因此今日要求如下：

1. 板载 Boot 按钮可以作为临时按钮输入源。
2. 只能在系统正常启动后，把它当普通输入使用。
3. 不允许在上电和复位阶段依赖长按 Boot 进行业务触发。
4. 如果 Boot 键干扰下载、启动或运行稳定性，则立即切换为外接按键到普通 GPIO。

结论：
- 今日方案默认优先使用 Boot 按钮做最小验证。
- 但文档必须把它标注为“临时测试方案，不是最终产品方案”。

## 3. 今日 MVP 目标定义

### 3.1 唯一核心目标
完成以下最小闭环：

开发板按钮按下 -> BLE 通知到小程序 -> 小程序界面显示 -> 小程序调用云函数 -> 云函数写数据库与云存储 -> 云函数调用大模型 -> 小程序显示模型返回文本

### 3.2 今日不做的事
今天不做以下内容：

1. 不做真实呼吸算法。
2. 不做真实心率算法。
3. 不做长时间后台蓝牙保活。
4. 不做音频流上传。
5. 不做 TTS 播放。
6. 不做硬件从云端拉命令。
7. 不做完整账号体系。

### 3.3 今日完成后的价值
今天完成后，可以确认：

1. 硬件直连小程序的 BLE 路线可行。
2. 小程序到云函数的调用可行。
3. 云函数到数据库/云存储的落盘可行。
4. 云函数代理调用大模型的方式可行。
5. 之后接入真实呼吸、心率数据时，不需要再重新选技术路线。

## 4. 推荐最小架构

### 4.0 目录放置要求
为避免影响当前仓库里已经存在的其他固件实验环境和前端内容，今天这条最小闭环建议按以下目录隔离：

1. 硬件侧独立目录
   - 建议目录：src/xiao_esp32s3plus_ble_button_link/
   - 作用：只存放“按钮事件 BLE 打通”这条最小链路的板端代码

2. 小程序侧独立目录
   - 建议目录：web/miniapp_ble_link_test/
   - 作用：只存放这次链路验证用的小程序模板与云函数接入代码

3. PlatformIO 独立 env
   - 建议 env 名称：xiao_esp32s3plus_ble_button_link
   - 作用：通过独立 build_src_filter 只编译本次链路代码，不影响当前已有 blink、IMU、PPG、LRA 等环境

说明：
- 当前仓库已经存在多独立 env 结构，因此本次不建议新开一个完全独立的第二个 PlatformIO 根工程。
- 更合理的方式是在当前 platformio.ini 里新增一个独立 env，并把源码隔离到专用子目录。
- 小程序则建议放在 web 目录下新增单独子目录，不与 ref 中旧项目混放。

### 4.1 总体结构
建议今天采用如下结构：

1. XIAO ESP32S3 Plus
   - 作为 BLE Peripheral
   - 暴露一个自定义服务
   - 暴露一个按钮事件通知特征

2. 微信小程序
   - 作为 BLE Central
   - 扫描并连接开发板
   - 订阅按钮事件特征
   - 收到事件后更新页面显示
   - 立即调用云函数提交事件

3. 云函数
   - 接收按钮事件
   - 写入数据库
   - 同时写一份 JSON 留痕到云存储
   - 代理调用一次大模型
   - 把结果返回给小程序

### 4.2 今日链路顺序
建议严格按以下顺序验证：

1. BLE 打通
2. 小程序页面显示打通
3. 云函数调用打通
4. 数据库写入打通
5. 云存储留痕打通
6. 大模型代理打通

不允许颠倒顺序，否则出问题时难以定位。

## 5. 硬件侧要求

### 5.1 角色定义
开发板今天只承担 2 个职责：

1. 广播并允许小程序连接。
2. 在按钮按下时发出一条 BLE 事件通知。

### 5.2 按钮事件定义
建议按钮事件最小字段为：

- event_type: button_press
- press_count: 第几次按下
- device_id: 固定测试设备名或设备编号
- firmware_time_ms: 板端时间戳或 millis

### 5.3 BLE 服务要求
建议先定义一套测试用 UUID，后续真实项目可替换。

建议至少包含：

1. Service UUID
   - 自定义测试服务

2. Notify Characteristic
   - 用于推送按钮事件

3. Read Characteristic
   - 用于读取设备信息，例如 device_id、firmware_version

### 5.4 板端行为要求
1. 上电后开始 BLE 广播。
2. 连接成功后允许通知按钮事件。
3. 每按一次按钮，只发送一次完整事件。
4. 必须做简单去抖，避免一次按下触发多条事件。
5. 串口要打印连接状态与按钮发送状态，便于调试。

## 6. 小程序端要求

### 6.1 页面目标
小程序首版只需要一个主页面即可，页面至少显示：

1. 蓝牙状态
   - 未初始化
   - 扫描中
   - 已发现设备
   - 已连接
   - 已订阅

2. 按钮事件状态
   - 最近一次按钮事件时间
   - 累计收到次数
   - 最近一条事件原始内容

3. 云端处理结果
   - 数据库写入是否成功
   - 云存储 fileID 或 cloudPath
   - 大模型返回文本

### 6.2 小程序模块要求
建议至少拆成以下逻辑模块：

1. BLE 初始化模块
   - 打开蓝牙适配器
   - 监听适配器状态

2. BLE 扫描模块
   - 扫描开发板
   - 按设备名或服务 UUID 过滤

3. BLE 连接模块
   - 建立连接
   - 获取 service 与 characteristic
   - 开启 notify

4. 事件处理模块
   - 解析按钮事件
   - 更新界面状态
   - 调用云函数

5. 云调用模块
   - 调用 link_test_ingest 云函数
   - 处理返回结果

### 6.3 小程序端边界
今天的小程序不负责：

1. 直接持有大模型密钥。
2. 直接写第三方模型 API。
3. 本地持久缓存复杂数据。
4. 长时间后台蓝牙策略。

## 7. 云函数要求

### 7.1 建议云函数名称
建议今天只建一个主云函数：

- link_test_ingest

它统一完成：

1. 接收按钮事件
2. 写数据库
3. 写云存储
4. 调用大模型
5. 返回处理结果

后续再拆分为多个正式函数。

### 7.2 入参要求
建议入参至少包含：

- user_id 或 openid
- device_id
- event_type
- press_count
- device_timestamp
- miniapp_timestamp

### 7.3 数据库写入要求
建议新建集合：

- link_test_events

建议字段：

- created_at
- openid
- device_id
- event_type
- press_count
- device_timestamp
- miniapp_timestamp
- llm_status
- llm_reply
- storage_file_id
- storage_cloud_path

### 7.4 云存储留痕要求
今天必须显式打通云存储。

建议做法：

1. 云函数把当前按钮事件和模型返回结果整理成一个 JSON 对象。
2. 云函数将该 JSON 序列化为 Buffer。
3. 通过云函数 uploadFile 写入云存储。

建议路径：

- link-test/YYYYMMDD/device_id/timestamp.json

这样今天就能确认云存储链路也通了，而不需要等待真实传感器文件。

### 7.5 大模型代理要求
今天只要求成功代理调用一次大模型，不要求模型能力复杂。

推荐提示词方向：

“收到来自 device_id 的第 N 次按钮按下事件，请返回一句 20 字以内的确认文本，说明链路已通。”

输出目标：

- 返回一段简短可见文本
- 例如：已收到按钮事件，蓝牙与云端链路验证成功

### 7.6 安全要求
1. 大模型 API Key 只能放在云函数环境或服务端安全配置中。
2. 小程序前端不能出现第三方模型密钥。
3. 云函数要打印必要日志，但不打印敏感密钥。

## 8. 今日数据流

### 8.1 端到端流程
1. 开发板启动 BLE 广播。
2. 小程序扫描到开发板并连接。
3. 小程序订阅按钮特征通知。
4. 用户按下开发板按钮。
5. 开发板发送按钮事件通知。
6. 小程序解析通知并更新页面。
7. 小程序调用 link_test_ingest 云函数。
8. 云函数写数据库。
9. 云函数写云存储 JSON 留痕。
10. 云函数调用大模型。
11. 云函数把数据库写入状态、存储信息、模型回复一起返回。
12. 小程序显示最终结果。

### 8.2 成功判据
只有以下全部成立，今天才算真正打通：

1. 板端按钮按下后，小程序界面计数加 1。
2. 云数据库能看到新纪录。
3. 云存储能看到新 JSON 文件。
4. 小程序能显示大模型返回文本。

缺一项都不算完成。

## 9. 实施顺序要求

### 9.1 第一步：板端 BLE 广播与通知
先不接云端、不接小程序复杂页面，只完成：

1. 开发板广播
2. 小程序能连上
3. 按钮按下有通知

### 9.2 第二步：小程序界面显示
完成：

1. 已连接状态显示
2. 按钮事件次数显示
3. 最近一次事件原始数据显示

### 9.3 第三步：云函数与数据库
完成：

1. 小程序收到事件后调用云函数
2. 数据库成功写入

### 9.4 第四步：云存储留痕
完成：

1. 云函数额外写一份 JSON 到云存储
2. 返回 fileID 或 cloudPath

### 9.5 第五步：大模型代理
完成：

1. 云函数调用大模型
2. 小程序页面显示结果

## 10. 验收标准

### 10.1 板端验收
1. BLE 广播稳定可发现。
2. 小程序能成功连接。
3. 每次按键只触发一次事件。

### 10.2 小程序验收
1. 页面能显示 BLE 状态。
2. 页面能显示按钮累计次数。
3. 页面能显示云函数返回结果。

### 10.3 云端验收
1. 数据库产生新记录。
2. 云存储出现新 JSON 文件。
3. 大模型调用返回非空文本。

### 10.4 整体验收
现场演示时，按下开发板按钮后 3 秒到 10 秒内，小程序应能看到：

1. 事件次数增加
2. 云端处理成功
3. 一句模型返回确认文本

## 11. 风险与替代方案

### 11.1 板载 Boot 按钮风险
因为 Boot 是 GPIO0 启动绑带脚，可能存在以下风险：

1. 下载时行为冲突
2. 复位阶段误入下载模式
3. 业务逻辑与启动脚复用带来偶发异常

替代方案：

1. 外接一个普通按键到非绑带 GPIO
2. 或先用串口命令模拟一次按钮事件，仅用于调试云端

### 11.2 小程序 BLE 风险
1. 安卓和 iOS 表现可能不同。
2. 权限未开会导致扫描失败。
3. notify 开启失败会造成“已连接但无事件”。

### 11.3 云端风险
1. 云函数环境变量未配置好会导致 LLM 调用失败。
2. 云存储权限或路径问题会导致留痕失败。
3. 数据库权限配置错误会导致写入失败。

## 12. 今日完成后下一步如何衔接
今天一旦完成，就可以直接往真实业务替换：

1. 把按钮事件替换为呼吸摘要上报。
2. 把单次按钮文本替换为心率/呼吸事件记录。
3. 把简单确认提示词替换为正式报告生成提示词。

因此今天的目标不是临时玩具，而是正式链路的最小骨架。
