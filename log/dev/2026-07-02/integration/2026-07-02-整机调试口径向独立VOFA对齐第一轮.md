# 整机调试口径向独立VOFA对齐第一轮

## 记录时间
- 日期：2026-07-02
- 模块：integration / resp / ppg / miniapp debug

## 任务名称
- 排查并修正整机联调页面与独立呼吸、独立 MAX30102 VOFA 调试环境口径不一致的问题

## 修改文件
- include/integration_types.h
- src/integration/resp_calibration_manager.cpp
- src/integration/active_test_manager.cpp
- src/integration/data_packager.cpp

## 主要结论
1. 这次确认“对不上”的主因不在 BLE 通知链路，也不在小程序画布绘图，而在整机源头发出的调试量与独立实验环境根本不是同一口径。
2. 呼吸侧原先只发 `resp_signal_value`、粗略 `resp_rate_bpm` 和简化幅度，没有带出独立环境用于观察的 `carrier`、`detrended`、检测低通与斜率等中间量。
3. PPG 侧原先只把 `heartRateEstimator.filteredIr()` 的结果做偏移后输出为 `latest_point`，而独立 VOFA 环境观察的是更完整的 `raw -> average -> detrended -> filtered * displayGain` 调试链。

## 主要变更
1. 扩展 `CalibrationStatusSnapshot`，新增 `respCarrierValue`、`respDetrendedValue`、`respSlopeValue` 字段。
2. 扩展 `ActivePpgRealtimeSnapshot`，新增 `rawIr`、`rawRed`、`averageIr`、`averageRed`、`detrendedIr`、`filteredIr` 字段，并把 `latestPoint` 改为浮点显示值。
3. 呼吸整机链路新增首轮锁轴逻辑，进入运行后固定使用当前主轴，不再每帧跟着重选 X/Y/Z。
4. 呼吸整机链路新增检测低通、warmup、峰谷确认阈值与幅度门限，尽量靠近独立呼吸环境的峰谷触发思路，而不是只靠单一 slope 过零估 BPM。
5. PPG 整机链路新增独立显示滤波状态，按 `dc alpha`、`signal alpha` 和 `display gain` 生成更接近独立 VOFA 观测口径的实时曲线值。
6. BLE `resp_debug`、`calibration_status`、`active_realtime` 的 JSON 打包同步补齐上述中间量，方便小程序继续直接消费。

## 实现思路
- 这轮不直接大改独立算法整段搬运，而是优先做“最小可验证对齐”：先把整机发送的数据种类和显示滤波链拉到与独立环境更接近的层级。
- 这样如果后续曲线仍有差异，就可以明确把问题继续收敛到“检测算法细节”而不是“传输字段不对”或“前端画错了”。

## 待确认事项
1. 这轮只是“调试口径对齐第一轮”，还没有把独立呼吸环境中的完整 reject reason、校准阶段状态机和全部运行指标完整搬入整机版。
2. PPG 实时曲线现在已改成更接近 VOFA 的显示链，但 BPM 计算仍然复用整机当前 `HeartRateEstimator`，若数值还偏，需要继续对比独立 MAX30102 工程中的 beat 判定与窗口策略。
3. 小程序页面当前虽可继续使用新增字段，但还没有把这些中间量分别拆成更多独立调试窗；若后续需要更像 VOFA，可再补多通道显示。

## 下一步建议
1. 先重新烧录并实测新版 `resp_debug` 与 `active_realtime`，确认小程序曲线是否已经明显接近独立 VOFA。
2. 若呼吸 BPM 仍不稳，下一步应继续把独立呼吸环境中的 reject reason 与 accepted cycle 条件完整同步到整机版。
3. 若 PPG BPM 仍偏差大，下一步应直接逐项对照独立 MAX30102 VOFA 工程的峰谷判定、beat stale 和接触判定逻辑。
