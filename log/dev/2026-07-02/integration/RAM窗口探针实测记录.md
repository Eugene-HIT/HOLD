# RAM窗口探针实测记录

## 头部信息
- 创建时间：2026-07-02
- 最后更新时间：2026-07-02
- 对应环境：`xiao_esp32s3_ram_window_probe`
- 文档目的：记录 XIAO ESP32S3 在整机联动方案下对 1 分钟业务窗口、主动检测处理波形和 raw 数据缓存的实际 RAM 承载结果，为后续 BLE 分片与窗口策略定版提供依据。

## 1. 实测结论

本次实测结果说明：

1. 当前板卡可识别 `PSRAM=YES`。
2. 在本轮代表性数据结构下，`1 分钟被动窗口 + 1 分钟主动处理波形 + beat 时间点` 可以稳定分配。
3. 在同一轮中额外附带 `raw ir/red` 两路降采样数据，也可以稳定分配。
4. 即使把被动缓存提升到 `3 个窗口` 级别，本轮代表性场景仍可稳定分配。
5. 当前阶段的主要瓶颈已不再是 RAM，而更可能是 BLE 分片发送节奏、小程序接收吞吐和组包稳定性。

## 3. 工程解释

这组结果意味着：

1. `1 分钟业务窗口` 作为默认业务口径是成立的。
2. `processed wave + beat + optional raw ir/red` 作为主动检测的默认缓存方案也是成立的。
3. 被动监测没有必要因为 RAM 顾虑而直接降到“只能秒级缓存”的极限保守方案。
4. 但这不等于可以把 `1 分钟整窗` 作为单次 BLE 发送单位，传输层仍建议保持 `10s` 到 `20s` 分片。

原因：

1. 本次验证的是 RAM 分配能力，不是 BLE 吞吐能力。
2. 小程序端对连续二进制分片的接收、缓存和重组仍需单独验证。
3. 真正接入传感器后，还会叠加运行时对象、BLE 栈、日志缓存和业务模块自身常驻内存。

## 4. 对规划的影响

根据本次结果，建议把后续默认策略收敛为：

1. 业务口径：继续保留 `1 分钟窗口`。
2. 被动传输：默认 `10s` 分片，必要时可放宽到 `15s` 或 `20s`。
3. 主动传输：默认先发处理后波形和 beat，raw `ir/red` 作为默认可带但可裁剪字段。
4. 缓存策略：允许本地保留 `1 分钟业务窗口 + 当前主动检测窗口`，不再把 RAM 当作首要否决项。

## 5. 下一步验证重点

下一步不应继续优先做 RAM 试探，而应转向 BLE 联调验证：

1. 验证 `10s` 分片在微信小程序侧的接收完整率。
2. 验证 `15s`、`20s` 分片是否会影响通知稳定性和前端渲染节奏。
3. 验证主动检测携带 raw `ir/red` 时，小程序端的组包与入库耗时。
4. 验证 BLE 状态包、校准包和波形分片并发发送时是否互相抢占。

## 6. 当前建议结论

可以进入下一阶段：

1. 允许按实施规范开始整机统一入口和数据结构编码。
2. 不需要再因为“ESP32 可能内存不够”而回退到过度简化的数据方案。
3. 传输层仍应保持分片架构，避免把 RAM 结论误用成“大包直发”的依据。
