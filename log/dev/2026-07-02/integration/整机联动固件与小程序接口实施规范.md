## 2. 本轮实现边界

本轮推荐先完成以下交付：

1. 新增整机联动统一入口环境。
2. 建立状态机、LED、震动、压力触发、BLE 状态通知五个基础模块。
3. 将当前呼吸校准输出整理为 `calibration_status` 结构。
4. 将当前被动呼吸输出整理为 `passive_resp_sample` 结构。
5. 将当前指部主动检测输出整理为 `active_ppg_sample` 与 `active_test_complete` 结构。
6. 小程序首页与校准页先打通 `device_state` 和 `calibration_status` 两条链路。
7. 用 RAM 探针环境验证“1 分钟业务窗口 + 分片发送”的默认策略是否可承受。

1. `main.cpp` 只负责初始化、tick 调度和高层状态切换，不直接写复杂算法。
2. 状态机模块只做状态判断、超时、迁移和外部命令接入，不直接读硬件寄存器。
3. 传感器管理模块只负责采样、处理和输出快照，不直接决定页面跳转。
4. BLE 模块只负责连接、订阅、写命令、发包，不负责业务判定。
5. `data_packager` 统一处理序列化，避免每个模块自己拼字符串。

## 6. 主循环落地方式

### 6.1 main.cpp 推荐结构

```cpp
void setup() {
  setupSerial();
  setupBoardPins();
  setupBleLinkManager();
  setupLedFeedbackManager();
  setupHapticFeedbackManager();
  setupPressureTriggerManager();
  setupRespCalibrationManager();
  setupPassiveMonitorManager();
  setupActiveTestManager();
  deviceStateMachineBegin();
}

void loop() {
  const uint32_t nowMs = millis();

  bleLinkManagerTick(nowMs);
  ledFeedbackManagerTick(nowMs);
  hapticFeedbackManagerTick(nowMs);
  pressureTriggerManagerTick(nowMs);
  respCalibrationManagerTick(nowMs);
  passiveMonitorManagerTick(nowMs);
  activeTestManagerTick(nowMs);
  deviceStateMachineTick(nowMs);
  publishPeriodicSnapshots(nowMs);
}
```

### 6.2 tick 顺序约束

1. 先处理 BLE 连接和命令输入。
2. 再更新传感器与压力状态。
3. 再运行状态机。
4. 最后根据状态机输出更新灯效、震动和 BLE 周期通知。

原因：

1. 状态机需要基于本轮最新输入做判断。
2. 灯效和发包需要反映状态切换后的结果。

## 8. BLE 传输实施要求

### 8.1 特征划分建议

建议使用 5 个特征：

1. `device_state_char`
2. `calibration_status_char`
3. `passive_stream_char`
4. `active_stream_char`
5. `debug_log_char`

### 8.2 编码策略

建议采用混合编码：

1. `device_state_char`：JSON UTF-8
2. `calibration_status_char`：JSON UTF-8
3. `passive_stream_char`：二进制分片帧
4. `active_stream_char`：二进制分片帧
5. `debug_log_char`：纯文本 UTF-8

这样做的原因：

1. 状态和校准提示字段短、易调试，JSON 足够。
2. 波形和 beat 点列表若仍用 JSON，BLE 包体膨胀明显，不利于分片效率。
3. 调试页读取纯文本最省开发成本。

### 8.3 二进制帧头建议

```cpp
struct PacketHeader {
  uint16_t schemaVersion;
  uint16_t packetType;
  uint32_t sessionId;
  uint32_t objectId;
  uint16_t fragmentIndex;
  uint16_t fragmentTotal;
  uint32_t windowStartTsMs;
  uint32_t windowEndTsMs;
  uint16_t payloadBytes;
  uint16_t reserved;
};
```

约束：

1. `objectId` 对被动数据表示 `window_id`，对主动数据表示 `measurement_id`。
2. `fragmentIndex` 从 `0` 开始。
3. 小程序只有在 `fragment_index + 1 == fragment_total` 且前序片段齐全时才允许组包完成。

### 8.4 分片发送策略

1. `device_state` 按 `250ms` 节拍发送。
2. `calibration_status` 按 `200ms` 节拍发送。
3. 被动数据每 `10s` 组一个传输片段，但逻辑归属同一 `1min window_id`。
4. 主动数据优先每 `5s` 或 `10s` 发一次处理后波形分片。
5. 原始 `ir/red` 只在剩余 RAM 和 BLE 吞吐满足条件时追加发送。

1. `device_state.status_text`

校准页只订阅两类数据：

1. `device_state`
2. `calibration_status`

校准页禁止直接依赖调试页文本，避免把日志当业务协议。

### 10.3 调试页数据源

调试页可订阅：

1. `debug_log_char`
2. `device_state_char`
3. 传感器初始化失败事件

调试页展示形式建议保留原始时间戳和原始文本，不做用户化改写。

## 11. RAM 探针实施说明

### 11.1 探针环境

已新增环境：

1. `xiao_esp32s3_ram_window_probe`

对应入口：

1. `src/xiao_esp32s3_ram_window_probe/main.cpp`

### 11.2 探针当前覆盖场景

1. `minute-lite`
   - 1 个 1 分钟被动窗口
   - 1 个主动处理后窗口
   - 不带 raw ir/red

2. `minute-with-raw`
   - 1 个 1 分钟被动窗口
   - 1 个主动处理后窗口
   - 附带 raw ir/red

3. `multi-window-fragment-cache`
   - 3 个被动窗口缓存
   - 1 个主动处理后窗口
   - 附带 raw ir/red

### 11.3 判定规则

建议以以下规则判断：

1. 若 `minute-lite` 稳定成功，说明“1 分钟业务窗口 + 处理后摘要”可作为默认下限。
2. 若 `minute-with-raw` 稳定成功，主动检测可考虑附带部分 raw ir/red。
3. 若 `multi-window-fragment-cache` 失败，则不要把“多分钟完整整窗缓存”作为默认策略，应改为边采边分片发。

### 11.4 2026-07-02 实测结果

根据本次用户提供的实测输出：

1. 板卡识别到 `PSRAM=YES`。
2. `minute-lite` 成功，`total_bytes=5704`。
3. `minute-with-raw` 成功，`total_bytes=17704`。
4. `multi-window-fragment-cache` 成功，`total_bytes=23864`。
5. `free heap before=373276`，最重场景 `after_alloc_ok=349300`。

据此更新本文件默认实现建议：

1. `1 分钟业务窗口` 可以作为默认缓存策略保留。
2. 主动检测默认允许附带 raw `ir/red` 降采样数据，但应保留裁剪开关。
3. 传输层仍默认采用 `10s` 分片，不因为 RAM 充足而改成“1 分钟整窗单次直发”。
4. 下一项必须验证的问题已从“RAM 是否够用”切换为“BLE 分片与小程序组包是否稳定”。

## 12. 实施顺序建议

1. 先建立 `integration_types.h` 和 `device_state_machine`。
2. 再接 `ble_link_manager`，先打通 `device_state` 和 `calibration_status`。
3. 再把压力触发、倒计时、LED、马达接入状态机。
4. 然后接被动窗口和主动窗口的分片发送。
5. 并行运行 RAM 探针环境，记录不同场景的实测结果。
6. 最后让小程序首页、校准页、调试页分别接对应特征。

## 13. 验收口径

只有满足以下条件，才算进入“可持续编码阶段”：

1. 新整机入口已不依赖旧实验环境的串口打印作为核心协议。
2. 状态机和传感器模块之间已有明确结构体边界。
3. 小程序首页与校准页已能独立消费正式字段，不靠正则拆日志。
4. RAM 探针至少跑通一组 1 分钟窗口基线场景。

## 14. 待实测补数项

1. 1 分钟 `PassiveRespWindow` 实际需要的点密度是否维持在 `300` 点即可满足显示。
2. 1 分钟主动检测的 `processedPoints` 取 `1500` 点是否过高或偏低。
3. BLE 二进制分片在微信小程序侧的接收和组包性能上限。
4. BLE 状态包、校准包与波形分片并发发送时的优先级冲突情况。
