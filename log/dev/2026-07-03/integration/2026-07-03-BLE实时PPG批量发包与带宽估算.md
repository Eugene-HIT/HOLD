## 已确认结论
1. 既有 RAM 探针记录已经明确：当前主要瓶颈不是 RAM，而是 BLE 分片发送节奏、小程序接收吞吐和组包稳定性。
2. 胸口 MAX30102 独立 VOFA 数据说明已经明确：当前胸口调试链是约 10ms 一帧，也就是约 100Hz 时间分辨率。
3. 旧整机联调实现按“每个新样本就发一个 JSON notify”，在胸口 PPG 场景下会把 100Hz 样本直接映射为约 100 次 notify/秒。

## 带宽推算

### 旧方案
- 单点实时 JSON 示例长度约：232 字符
- 样本节拍：约 10ms / 点
- notify 频率：约 100 次 / 秒
- 文本发送量估算：约 23200 字符 / 秒，约 23KB/s

### 新方案
- 批量实时 JSON 示例长度约：211 字符
- 每包携带：5 个样本
- 批量周期：约 50ms / 包
- notify 频率：约 20 次 / 秒
- 文本发送量估算：约 4220 字符 / 秒，约 4.2KB/s

### 结果解释
1. 单包长度没有压到旧方案的五分之一，但每包承载 5 个样本，因此折算后单样本文本成本已从约 232 字符降到约 42 字符。
2. notify 频率从约 100 次/秒降到约 20 次/秒，对微信小程序中心端更友好。
3. 该方案仍保留 10ms 级样本时间分辨率，没有把波形本身降采样到 20Hz 或 25Hz。

## 主要变更
1. 新增 `ActivePpgRealtimeBatch`，固定每批携带 5 个样本。
2. 主动 PPG 管理器不再逐样本直接发 BLE，而是把 `I6/I7` 实时点先写入批量缓存，满 5 点后输出一包。
3. 批量 JSON 改为紧凑字段：
   - `i6`：I6 数组
   - `i7`：I7 数组
   - `bpm` / `qs` / `bc` / `cp`
4. 小程序 runtime 支持一次性解析一个批量包并向波形缓存追加多个点。
5. 调试页重绘节奏由约 60fps 放宽到约 30fps，避免批量到包后频繁重绘抢占主线程。

## 实现思路
- 这次选择的是“小批量攒包”而不是“继续逐点发送但加大节流”。
- 原因是加大节流会直接丢时间分辨率，而批量攒包能同时保留样本细节和降低 notify 频率。
- 当前固定为 5 点/包，是在 100Hz 样本节拍和微信小程序 BLE 稳定性之间的保守折中。
