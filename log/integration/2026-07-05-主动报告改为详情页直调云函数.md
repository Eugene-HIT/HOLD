# 2026-07-05 主动报告改为详情页直调云函数

## 任务名称
针对指部 PPG 报告长期卡在 preview/stored 中间态、无法稳定生成的问题，改为与日报页/总结页一致的详情页直接调用云函数流程

## 修改文件
- web/pages/active-report/index.js

## 主要变更
- 详情页新增 buildActiveReportPrompt()，在页面内直接基于当前主动记录构造 prompt
- 详情页 generateReport() 不再调用 runtime 的 requestActiveMeasurementInsight() 包装链
- 详情页改为直接使用 wx.cloud.callFunction({ name: 'health_insight', report_kind: 'active_report' })，与日报页/总结页调用方式保持一致
- 云函数返回后的 reply_text / source / error_message / 更新时间直接写回当前详情页 viewReport，用于当前页展示
- 调试信息改为 direct=1 + source/error/code，直接反映最短云调用链结果
- 主动报告提示词目标从“节律/数据局限说明”调整为“焦虑、紧张、压力激活倾向解读优先”，仅在低置信度时附带简短说明数据质量问题
- 详情页生成报告后，会同时把结果写入本地页面 patch 与 runtime.activeMeasurements，避免订阅刷新把刚生成的文本冲掉
- 详情页 preview 显示条件从“仅测试进行中”调整为“本页已见过本轮主动检测后持续保留”，修复 60 秒结束瞬间跳进空页的问题
- 修复主动报告 HRV 输入缺失：preview 报告对象现在会携带 beat 时间点与 RR 间期，runtime.latestActiveWindow 也会直接缓存本轮完整 HRV 输入
- 生成报告前会再次归一化 HRV 字段，成功或失败后的调试信息会直接显示本次实际上送给模型的 beat 数与 RR 数
- 确认并修复 beat 来源问题：当前小程序不再自行根据波形重算主动检测 beat，优先使用固件主动检测链直接发送的 beat 时间戳
- 固件主动检测补充 beat 融合逻辑，并恢复在 active_window 单包内发送完整 beat_ts_ms 数组，避免前端只能依赖 i7 标记流近似还原
- 修复详情页显示口径仍吃旧 i7 marker 的问题：跳点绘制、beat 数统计、preview 显示统一改为优先按固件 beat 时间戳重建，不再让原始 i7 spike 抢主位
- 将主动检测固件的 beat 判定链彻底回退并对齐到独立指部 VOFA 口径：移除放宽版手指 profile 与额外 beat 融合状态机，恢复直接使用默认手指 HeartRateEstimator 判定
- 根据用户最新要求，主动检测进一步直接切换为与胸口 PPG 实时链完全同款的 profile、显示滤波和 beat marker 输出口径
- 根据用户进一步要求“删了重做”，主动检测管理器已整文件重写为与胸口 PPG 实时链同构的实现，只保留主动检测特有的 60 秒窗口累计与 beatTsMs 记录
- 进一步修复主动检测新旧记录串号问题：主动记录 ID、首页跳转 ID、详情页 fallback ID 统一改为 `session_id + measurement_id`，避免重启后新的 measurement_id 与旧缓存复用成同一条记录

## 本次判断与结论
用户明确指出：
1. 总结报告和呼吸/胸口 PPG 已经能调用生成
2. 指部主动报告不应继续卡在 runtime 包装链的 preview/stored 中间态
3. 既然当前只传 beat 时间点，数据量已经很小，再继续怀疑输入大小没有意义
4. 当前已能生成报告，但内容偏成“数据质量评价”，没有围绕焦虑/紧张状态输出有效结论

本次因此不再沿用 requestActiveMeasurementInsight() 的中间态封装，而是让详情页自身走和日报页/总结页同样的直接调用路径。这样可以把问题收缩到：
- 云函数本身是否能被正确调用
- 云函数是否返回了可解析的 result.result
- 页面是否正确展示了 source / error_message

在调用链打通后，提示词又进一步调整为：
- 优先判断本次检测更偏向放松平稳、轻度紧张、明显紧张，还是暂时无法可靠判断
- 重点围绕自主神经紧张程度、HRV 偏低倾向、节律发紧与压力激活倾向来写
- 数据质量不再作为主叙事，只有明显低置信度时才简短降级说明

在页面状态层，本次又补了两处：
- 报告生成成功后，不能只 setData(viewReport)，否则下一次 runtime emit 会被旧 state 覆盖
- 60 秒主动检测结束后，currentDeviceState 会退出 ACTIVE_TEST_STATE，但 latestActiveWindow 仍是刚测完那条，因此详情页不应立刻切到“当前没有数据”空态

在 HRV 链路层，本次进一步确认并修复：
- 问题不是云函数没调用，而是详情页处于 preview=1 / stored=0 时，传给 prompt 的对象可能缺失 beatTimelineMs / rrIntervalsMs
- 仅依赖页面实时小窗或 240 点可视化窗口推导 HRV 不可靠，因此改为在 runtime.applyActiveWindow() 阶段就生成并缓存 beat_timeline_ms / rr_intervals_ms
- 详情页 buildActiveReportPrompt() 与 generateReport() 在上云前会优先读取已缓存 HRV，若缺失才做本地兜底推导
- 这样无论是首次跳转、停留页内生成、还是重新进入详情页，都不会再因为 preview 路径而把 HRV 输入丢空

在 beat 判定链路层，本次进一步确认并修复：
- 小程序详情页并没有独立做主动检测 beat 算法，之前看到的 beat 主要来自固件 `HeartRateEstimator` 结果，经 `active_realtime_batch.i7`、`bc` 和 `active_window.beat_ts_ms_fragment` 上送
- 之前为避开微信 BLE 上 32 片整窗不稳定，主循环把 `active_window` 改成了只发元数据空壳，导致前端拿不到完整固件 beat 时间戳，只能退回到 i7 marker 恢复节律时间线
- 当前已改为：`active_window` 单包直接补发完整 beat 时间戳数组；前端优先使用这份固件时间戳，而不是从显示波形自行判 beat
- 同时在固件主动检测中加入 beat 融合状态机：保留原 `HeartRateEstimator` 结果作为主来源，但当相邻已确认 beat 之间出现明显漏检空档时，允许用同一份固件滤波波形做有限补偿，减少“波形正常但 beat 数异常偏少”的情况

在详情页显示层，本次又确认并修复：
- 即使 runtime 已缓存 beat_timeline_ms，详情页画图和 fullBeatCount 之前仍优先使用 `ppgBeatMarkerPoints/fullPpgBeatMarkerPoints`，而这些字段在 preview 路径上仍来自旧的实时 i7 marker
- 这会导致“送模型的 HRV 输入可能已换成 beat 时间戳，但用户眼前图上的粉色跳点和 beat 数仍像没变一样继续乱跳”
- 当前已统一改为：优先根据固件 beat 时间戳重建 marker 序列，再用于画图、统计 beat 数和 preview 展示，确保页面视觉、计数和上云 HRV 输入三者一致

在主动检测固件算法层，本次进一步回退并统一：
- 用户明确要求：主动检测应老老实实参考独立指部 VOFA 固件的判定与发送方式，而不是继续叠加整机链上的额外实验性补丁
- 当前已将 `src/integration/active_test_manager.cpp` 回退到与 `src/max30102_xiao_esp32s3_vofa/main.cpp` 同口径：
  - 显示侧 DC/Signal alpha 改回 `project_config::kHeartRateDcAlpha / kHeartRateSignalAlpha`
  - 显示增益改回 `project_config::kMax30102VofaFilteredDisplayGain`
  - beat marker 改回 `heartRateEstimator.beatDetectedRecently() ? filteredPoint : 0.0f`
  - BPM 改回直接使用 `heartRateEstimator.bpm()`
  - beat 时间戳改回在 `heartRateEstimator.beatCount()` 增长时直接记录 `sample.capturedAtMs`
- 同时移除了我此前为主动链临时加入的 `buildRelaxedFingerProfile`、`ActiveBeatFusionState` 和相关辅助补偿逻辑，避免算法口径再偏离独立指部 VOFA

在用户明确要求“直接改成和胸口 PPG 一模一样”后，本次又进一步统一为胸口链口径：
- 主动检测现在直接使用与 `src/integration/passive_ppg_manager.cpp`、`src/max30102_xiao_esp32s3_chest_vofa/main.cpp` 相同的 `buildChestProfile()` 参数
- 主动检测显示滤波改为 `0.18 / 0.22 / 12.0` 组合
- beat marker 改为与胸口链同款的高可见事件脉冲 `1000.0f`
- 初始化与每次重新开始检测时都会显式 `setProfile(buildChestProfile())`

在用户继续指出“根本不明白什么叫一模一样”后，本次最终处理不是继续补丁，而是直接重写 `src/integration/active_test_manager.cpp`：
- 结构改为按 `src/integration/passive_ppg_manager.cpp` 同模版组织
- 重置逻辑拆成 `resetDisplayState / resetWindowState / resetRealtimeState`
- 测量启动逻辑拆成 `beginMeasurement()`
- 实时批发送逻辑拆成 `appendRealtimeBatch()`
- 主动链仅额外保留 `storeProcessedPoint()` 与 `storeBeatTimestamp()` 两个主动检测所需能力
- 前端构建标记已提升为 `active-report 2026-07-05-04`，用于确认真机加载的是本次重做后的页面版本

在继续排查“删了重做但页面看起来还是没变化”后，本次又确认并修复：
- 前端和 runtime 此前大量使用裸 `measurement_id` 作为主动记录 ID
- 该值在固件重启后会从 1 重新开始，导致新的主动检测极易与旧缓存记录复用同一条 ID
- 这会表现为：即使固件主动检测逻辑已经重写，页面仍可能继续显示旧缓存记录的图和 beat 数，肉眼感觉就像“根本没改”
- 当前已统一改为 `session-${session_id}-measurement-${measurement_id}` 形式，首页跳转、详情页 fallback、runtime.activeMeasurements 三处保持一致
