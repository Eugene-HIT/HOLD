# 多人协作工作网站调研与方案

## 头部信息
- 创建时间：2026-06-08
- 最后更新时间：2026-06-08
- 文档类型：方案调研 / 开发要求草案
- 文档目的：为“用于同步开发信息的多人协作工作网站”形成一份可直接执行的技术与上线方案，覆盖页面形态、模块边界、技术栈、域名与服务器流程、部署路径和待确认项
- 适用范围：小团队内部协作网站；核心需求为甘特图总览、点击查看详情、按成员颜色区分、任务支持文字与照片、多人同时使用
- 输入：用户口述需求；当前仓库开发协作约束；Next.js、Vercel、Supabase、Frappe Gantt、Cloudflare Registrar、腾讯云 ICP 官方资料
- 输出：推荐技术方案、部署方案、采购与上线流程、阶段实施计划、验收标准、待确认事项

## 1. 本次完成内容
本次调研围绕以下问题给出结论：

1. 这个网站做成什么形态最合适
2. 适合采用什么技术栈，才能既好看又不把开发复杂度拉太高
3. 域名、服务器、数据库、图片存储、多人协作分别应该怎么落
4. 如果要给国内团队稳定使用，备案和部署地区应该怎么判断

本次结论先行：

- 这是一个典型的轻量协作型 Web 应用，不建议从传统项目管理系统二次魔改起步
- 最适合的首版路线是：Next.js + Supabase + Frappe Gantt + 对象存储式图片上传
- 页面结构应采用“上方甘特图总览 + 右侧或弹层详情面板”的信息架构，而不是多页面跳转
- 该工具更适合定义为“进度记录墙”而不是“计划管理工具”，重点是记录谁做了什么、什么时候做的、留下说明和图片
- 多人协作可直接接入 Supabase Realtime，做到几个人联机后接近实时更新，不需要自建复杂 WebSocket 服务
- 若主要使用者在中国大陆，是否走国内云服务器方案，取决于你是否要求长期稳定访问和备案合规；若只是团队内部先跑起来，海外托管路径会更省事

## 2. 用户需求转译

### 2.1 已确认需求
- 首页以甘特图为主视图
- 点击任务后能看到详情
- 不同成员使用不同颜色表示
- 新增任务时可填写文字说明并上传照片
- 采用邮箱登录
- 不做任务状态流转，不做计划排期管理，只做开发记录与阶段总结
- 任务默认为已发生的记录项，重点展示时间、负责人、说明和图片
- 成员颜色尽量允许在注册或个人设置时自行定义
- 希望整体观感偏可爱、简约，允许加入像素风小动画
- 未来需要 2 到 3 人共同联网使用和维护

### 2.2 已确认示例内容
- 网站名称：HOLD 进度墙
- 示例记录：IMU开发
- 负责人：Eugene
- 时间：6.8 00:30-03:20
- 说明：开发学习式呼吸检测算法
- 图片：先使用 3 张占位图

### 2.3 隐含工程需求
基于以上表述，实际需要补上的能力包括：

- 用户登录，否则无法区分是谁在编辑和查看
- 任务数据持久化，否则多人协作无法成立
- 图片文件存储，否则照片无法长期访问
- 基本权限控制，否则任何人都能误改所有内容
- 联机更新，否则几个人同时使用时体验会很差
- 可部署到公网；正式域名不是首版必需项

### 2.4 暂未确认但必须预留的点
- 是否需要区分访客、普通成员、管理员
- 是否需要任务评论或仅保留任务描述
- 是否需要手机端只读或基础编辑能力
- 是否要求中国大陆访问速度优先

## 3. 推荐产品形态

## 3.1 页面结构
推荐采用单页式工作台：

- 顶部：网站标题、成员筛选、时间范围切换、添加记录按钮
- 主体：甘特图时间轴
- 侧边：记录详情抽屉，点击后展开
- 底部或次级区块：最近更新、图片缩略图、操作记录

这样做的原因是：

- 你的核心入口就是时间线，不需要复杂导航
- 点击即看详情比页面跳转更顺畅
- 后续增加筛选、搜索、项目切换也比较自然

### 3.2 视觉方向
建议不要做成传统 OA 或表格后台，应更偏“轻松的开发记录墙”：

- 浅色基底更合适，整体偏柔和、可爱、简约
- 记录颜色由成员颜色驱动，不再强调状态标签
- 图片展示应采用卡片缩略图，详情里支持放大查看
- 甘特图区域应保留足够留白和层次感，减少廉价管理系统感
- 可加入少量像素风动画或小装饰，但仅使用可商用或明确授权素材，不直接使用来源不明的动漫素材

## 4. 推荐技术方案

### 4.1 首选技术栈
- 前端框架：Next.js
- UI 层：自定义界面 + 设计系统组件
- 甘特图库：Frappe Gantt
- 时间处理：Day.js
- 后端能力：Next.js Route Handlers 或 Server Actions
- 数据库与登录：Supabase
- 图片存储：Supabase Storage
- 部署平台：Vercel
- 域名注册：Cloudflare Registrar 或 Vercel Domains

### 4.2 这样选的原因

#### Next.js
官方文档确认可以快速初始化完整 Web 项目，默认支持 TypeScript、App Router、图片资源、路由与部署工作流，适合从简单站点平滑长成带后端能力的协作应用。

#### Frappe Gantt
官方页面明确说明它是开源 JavaScript 甘特图库，具备以下与你需求直接相关的能力：

- 支持 Day、Hour、Year 等视图模式
- 支持可配置 popup
- 支持点击标题与交互
- 支持通过 API 或 HTML 自定义弹窗内容

这意味着它非常适合做“上面甘特图，点一下看详情”的核心交互。

#### Supabase
官方文档明确提供 Next.js 快速入门、数据库、认证和存储教程。对于你的场景，它可以一次性解决：

- 账号登录
- 任务表存储
- 成员信息存储
- 图片上传与访问

相比自己搭 Node.js + PostgreSQL + 文件服务，初期复杂度更低。

#### Vercel
官方文档明确支持连接 Git 仓库自动部署、预览环境和自定义域名。对首版协作网站来说，这能显著降低上线和迭代门槛。

### 4.3 不推荐的起步方案
- 不建议直接买现成项目管理 SaaS 再做深度定制，后续样式、流程和数据迁移都会受限
- 不建议首版就上复杂实时协作编辑、WebSocket 房间、多人同时拖拽同步，这会把开发难度抬高一个量级
- 不建议首版自建完整后端和文件系统，除非你明确要求所有数据必须自托管

## 5. 建议的数据结构

### 5.1 核心实体
- 用户：姓名、邮箱、角色、颜色
- 项目：项目名、描述
- 记录：标题、描述、负责人、开始时间、结束时间
- 附件：图片 URL、上传人、上传时间、所属记录
- 操作记录：谁在什么时间新增、修改、上传了什么

### 5.2 记录详情建议字段
- 记录标题
- 记录说明
- 负责人
- 起止时间
- 关联图片
- 最近更新时间
- 创建人

这已经足够支撑首版，不需要一开始做成完整项目管理系统。

## 6. 功能范围建议

### 6.1 首版必须做
- 登录
- 甘特图记录展示
- 点击查看记录详情
- 按成员颜色显示记录
- 新增记录
- 编辑记录
- 上传图片到记录详情
- 按成员筛选
- 联机后自动刷新或近实时同步更新

### 6.2 第二阶段再做
- 评论区
- 任务拖拽改期并自动保存
- 操作历史时间线
- 移动端优化编辑
- 通知提醒

### 6.3 暂不建议做
- 多项目复杂权限体系
- 富文本协作文档
- 即时聊天
- 复杂审批流
- 细粒度看板与工时系统

## 7. 多人协作怎么实现

### 7.1 最小可行协作方案
多人协作成立的关键不是“实时光标”，而是以下四件事：

- 所有人使用同一套线上数据库
- 每个人都有自己的账号
- 改动能即时保存
- 能追踪最近是谁改了什么

对你的目标而言，这就已经足够。

如果要更像“我这边一加，对方那边马上看到”，可以直接接入 Supabase Realtime。对 2 到 3 人的小范围使用，这条路线是合适的。

### 7.2 权限建议
- 管理员：创建项目、删除任务、管理成员颜色
- 成员：新增和编辑任务、上传图片
- 访客：只读查看

如果团队规模很小，也可以先只做“管理员 + 成员”两级。

## 8. 域名和服务器是否需要购买

### 8.1 域名
不是现在的必需项。

原因：

- Vercel 默认就会给一个可访问的网址，足够先做和先用
- 你现在只有 2 到 3 个人内部使用，先不上正式域名完全没问题
- 等确认这个工具会持续使用，再买域名更省钱

域名建议：

- 优先短、易拼写、无歧义
- 优先 .com，其次 .cn 或团队习惯后缀
- 如果只是内部使用，也可以先用二级域名

### 8.2 服务器
是否要买，取决于部署路径。

#### 路径 A：轻量云托管路径
- 前端和 API 部署在 Vercel
- 数据库与存储放在 Supabase
- 域名绑定到 Vercel

这种情况下，你不需要自己买传统意义上的云服务器 ECS 或 CVM。

#### 路径 B：自托管路径
- 自己购买云服务器
- 自己部署 Next.js、数据库、文件存储或对象存储
- 自己维护反向代理、HTTPS、备份和运维

只有在你明确要求自控性更高、国内访问更稳、或合规要求更强时，才建议走这条路。

## 9. 国内访问与备案判断

### 9.1 已确认的官方结论
腾讯云 ICP 官方文档明确给出了备案限制说明，并列出“是否需要备案”“备案概述”“未备案不得提供非经营性互联网信息服务”等相关文档入口。该组文档可作为中国大陆服务器上线前的备案判断入口。

### 9.2 对本项目的工程判断
可以按下面两种情况理解：

#### 情况 A：先内部使用、先快速上线
- 直接走 Vercel + Supabase
- 买域名并绑定即可
- 不走中国大陆云服务器起步

优点：
- 最快
- 最省运维
- 最适合先验证产品形态

风险：
- 中国大陆访问速度和稳定性不如国内云
- 若后续要长期公开使用，可能还要迁移

#### 情况 B：要给国内团队长期稳定使用
- 购买中国大陆云服务器或使用国内合规托管平台
- 提前准备备案流程
- 域名实名认证、主体信息、网站名称等都要按要求处理

优点：
- 国内访问通常更稳
- 更适合后续长期正式使用

代价：
- 上线流程更长
- 需要实名认证、备案资料、审核等待
- 还要承担服务器运维工作

### 9.3 建议选择
如果你现在还处在“把协作方式跑通”的阶段，建议先走情况 A。

等团队确认这个网站会长期使用，再决定是否迁移到国内云和备案，不要一开始就把流程压复杂。

## 10. 推荐落地路径

### 10.1 我推荐的首选路径
首选路径：

- 域名：首版可不买；后续如需正式访问，再在 Cloudflare Registrar、腾讯云或阿里云购买
- 网站部署：Vercel
- 前端与服务端：Next.js
- 甘特图：Frappe Gantt
- 数据库与登录：Supabase
- 图片：Supabase Storage

这是当前最平衡的一条路线。

原因：

- 你要的是轻量协作站，不是大而全项目管理平台
- 首版重点是好看、好用、可共享，不是自建复杂基础设施
- 这条路线可以很快做出可上线版本

### 10.2 备选路径
如果你从一开始就确定必须国内稳定访问，可改为：

- 域名：阿里云或腾讯云注册并实名认证
- 服务器：腾讯云 Lighthouse/CVM 或阿里云 ECS
- 部署：Next.js 自托管
- 反向代理：Nginx
- 数据库：托管 PostgreSQL 或 MySQL
- 图片：对象存储 COS/OSS

但这条路明显更重。

## 11. 上线过程应该怎么走

### 11.1 推荐流程
1. 先确认功能边界，只做一个项目或少量项目的首版
2. 画一个简单原型，确定甘特图、详情抽屉和新增弹窗
3. 建项目代码仓库
4. 初始化 Next.js 项目
5. 接入 Frappe Gantt 做假数据原型
6. 接入 Supabase，完成登录、记录表、图片上传和实时同步
7. 上线到 Vercel，先用默认域名内测
8. 邀请团队成员试用
9. 确认会长期使用后，再购买并绑定正式域名
10. 根据使用反馈决定是否补评论、移动端优化和操作记录

### 11.2 域名购买与绑定流程
1. 想好域名关键词
2. 在 Cloudflare Registrar 或 Vercel 搜索是否可注册
3. 完成域名注册和实名认证流程
4. 在部署平台绑定域名
5. 配置 DNS
6. 等待证书签发和解析生效

### 11.3 如果后续迁移到国内云
1. 准备备案主体资料
2. 完成域名实名认证
3. 购买中国大陆服务器
4. 提交备案
5. 审核通过后上线国内实例
6. 切换 DNS 到国内服务

## 12. 开发阶段计划

### 12.1 第一阶段：原型验证
- 输出高保真界面稿或接近成品的页面原型
- 用假数据把甘特图、详情、颜色、图片展示跑通
- 不接真实登录

### 12.2 第二阶段：协作最小闭环
- 接入登录
- 接入数据库
- 接入图片上传
- 实现新增、编辑、查看

### 12.3 第三阶段：正式上线
- 购买域名
- 绑定线上环境
- 补基础权限和错误处理
- 做一次团队试运行

### 12.4 第四阶段：体验优化
- 更细的筛选与搜索
- 最近更新记录
- 移动端浏览优化
- 更柔和的像素风动效与视觉细节

## 13. 验收标准
- 用户打开首页后，能直接看到清晰可用的甘特图
- 点击任一记录后，能在详情面板看到完整说明和图片
- 不同成员的记录颜色可稳定区分
- 成员登录后可以新增和编辑记录
- 图片上传后能长期访问，不因刷新丢失
- 多个成员能基于同一线上数据协作，并能看到近实时更新
- 管理员能控制基础权限
- 网站至少可通过默认线上地址访问

## 14. 风险与待确认事项

### 14.1 风险
- 如果直接走海外托管，中国大陆访问体验可能不稳定
- 如果一开始就走国内备案，上线周期会被拉长
- 如果图片上传不做压缩与尺寸限制，存储和加载体验会变差
- 如果首版功能扩太多，很容易从轻量协作站失控成重型管理系统

### 14.2 待确认事项
- 主要使用者是否都在中国大陆
- 是否必须支持手机端编辑
- 是否需要评论功能
- 是否需要多个项目共存
- 是否要求公司名义备案和长期正式运营

## 15. 最终建议
对你当前阶段，最合理的路线不是先研究服务器怎么买，而是先把产品形态和协作闭环跑通。

推荐执行顺序：

1. 先按 Vercel + Next.js + Supabase + Frappe Gantt 做首版
2. 先用默认线上地址给团队试用
3. 确认真的有人持续用，再买正式域名
4. 若确认要长期给中国大陆团队稳定使用，再评估迁移国内云与备案

这条路线能把你的试错成本、开发复杂度和上线时间同时控制在较合理范围内。
