# 2026-07-08 MCU 迭代方向调研

## 文档目的
评估 HOLD 后续版本是否有必要从当前 XIAO ESP32S3 / ESP32-S3 路线迁移到更强的 MCU/SoC，以支持更智能、可脱离手机独立使用的产品形态。

## 当前问题定义
用户目标不是单纯“换一颗更强芯片”，而是实现以下能力：
- 脱离手机时，设备端可以完成基础状态判断
- 设备端可以直接给出引导，例如灯光、震动、简单语音或节律提示
- 后续产品要有足够“智能感”，而不是完全依赖手机端云分析

因此本次判断的核心不是算力越大越好，而是判断：
- 当前 ESP32-S3 是否已经足够覆盖下一阶段目标
- 若不够，应该升级到哪一类主控，而不是盲目追求类似某竞品的“更强 MCU”

## 当前工程基线
结合当前仓库文档与实现，可以确认：
- 当前主控路线以 XIAO ESP32S3 / ESP32-S3 为核心
- 当前主要传感链路为 ECG / PPG / IMU / 压力 / 麦克风的组合验证
- 当前反馈链路已经具备 LED、LRA 震动、热反馈、BLE、小程序联调能力
- 当前产品阶段仍是 MVP / 可演示样机，而不是大规模量产前的硬件冻结阶段

这意味着当前系统最紧迫的瓶颈，未必是 MCU 算力，而更可能是：
- 哪些传感组合最稳定
- 哪些状态判断规则最有效
- 哪些反馈形式最能让用户感知“有用”
- 如何在设备端和手机端之间划分职责

## 外部资料与可确认结论

### 1. ESP32-S3
官方页面说明：
- ESP32-S3 是双核 Xtensa LX7，主频 240 MHz
- 具备 2.4 GHz Wi-Fi 与 Bluetooth 5 LE
- 有额外的向量指令，用于神经网络计算和信号处理加速
- 官方明确将其定位为 AIoT 应用，支持 ESP-DSP、ESP-NN、ESP-WHO、ESP-Skainet
- 具备 I2S、I2C、SPI、UART、PWM、ADC、触摸输入、ULP 低功耗核心等丰富外设

这说明：
- ESP32-S3 并不是“只能做联网壳子”的普通 MCU
- 对于传感器融合、简单规则判断、轻量级 TinyML、节律引导、本地 BLE/Wi-Fi 通信，它仍然是可用且成熟的选择
- 若只是要做“脱离手机也能完成简单判断和引导”，ESP32-S3 在能力上并没有天然不够

### 2. NXP i.MX RT1060
官方页面说明：
- Arm Cortex-M7，最高 600 MHz
- 1 MB 片上 SRAM
- 有多种外部存储接口
- 有 3 路 I2S、多媒体、显示、摄像头等更强 HMI / 音频能力
- NXP 还提供基于 i.MX RT1060 的官方本地语音控制方案，运行在 FreeRTOS 上，可接多路 MEMS 麦克风，并实现无云本地语音控制

这说明：
- i.MX RT1060 非常适合“本地语音 + 更复杂 UI + 更强边缘推理/音频前端”这类需求
- 但它通常不是一颗像 ESP32-S3 那样“无线一体”的低门槛 SoC，很多无线能力需要外挂方案
- 从工程复杂度上看，它更像“第二阶段产品主控”而不是“当前 MVP 立刻替换”的主控

### 3. Nordic nRF54H20
官方页面说明：
- 多个 Arm Cortex-M33 + RISC-V 协处理器，最高 320 MHz
- 2 MB NVM + 1 MB RAM
- 面向高级 wearable、医疗健康、BLE / Thread / Matter 设备
- 官方明确支持 ML models and sensor fusion at the edge
- 强项是超低功耗、强 BLE、多协议无线、可替代外部 flash + 无线 SoC + 应用 MCU 的一体化方案

这说明：
- 如果后续产品重点是“低功耗可穿戴 + 长续航 + 强 BLE + 本地传感融合”，nRF54H20 很值得作为候选路线
- 它比 ESP32-S3 更偏 wearable / BLE 中心化方案
- 但其开发迁移成本、生态迁移成本、现阶段团队熟悉度，都会明显高于继续沿 ESP32-S3 迭代

### 4. Ambiq Apollo4 Blue Plus
官方页面说明：
- Cortex-M4F，最高 192 MHz
- 集成 BLE 5.4
- 2 MB NVM + 2.75 MB 低功耗 RAM
- 明确面向 smart watches/bands、activity and fitness monitors、consumer medical devices
- 官方强调 activity recognition、speech enhancement、real-time health analytics
- 超低功耗是其核心优势

这说明：
- 如果后续产品高度强调“手环/挂件式低功耗可穿戴 + 本地健康分析 + BLE”，Apollo4 Blue Plus 非常贴近产品方向
- 它比 ESP32-S3 更像“消费级可穿戴专用低功耗平台”
- 但其开发生态、资料开放度、团队上手成本通常不如 ESP32-S3 直接

## 关于“类似 looki 一样用的 MCU”
本次无法可靠确认所谓“looki”具体使用哪颗 MCU，除非有：
- 官方硬件说明
- 明确拆解报告
- 可核实的 BOM / FCC / teardown 资料

因此本次不能把“looki 用了什么 MCU”当作确定依据。

能可靠给出的结论只有：
- 如果你说的那类产品强调独立使用、边缘判断、可能带语音或更自然的交互，它大概率属于“低功耗 AI SoC”或“高性能 crossover MCU + 无线方案”这一类，而不是简单的传统低端 MCU

## 核心结论

### 结论 1：现在没有充分必要立即换主控
如果你们下一阶段目标只是：
- 做本地基础判断
- 脱离手机给出灯光/震动/热反馈/简单节律引导
- 在设备端跑规则法或轻量 TinyML

那么当前 ESP32-S3 路线仍然够用，不建议现在立刻换主控。

原因：
- 当前真正未收敛的是传感路线、状态判断逻辑和产品交互方式，不是 MCU 已经成为绝对瓶颈
- 换主控会让你们同时重做：底层驱动、外设适配、功耗验证、BLE 链路、工具链、封装与电源设计
- 对当前阶段来说，这会显著拖慢产品验证，而不一定直接提升状态判断效果

### 结论 2：如果目标升级到“更强独立智能”，才值得换主控
只有当你们明确把产品目标升级为下面之一时，才值得认真迁移：
- 设备端常驻语音唤醒 / 本地关键词 / 本地语音引导
- 多麦克风音频前端、环境识别、降噪、声学状态判断
- 更复杂的本地模型，例如多模态融合 + 时序模型 + 长窗口分析
- 本地 GUI / 屏幕 / 动画交互成为核心体验
- 长续航要求显著提高，ESP32-S3 的 Wi-Fi / 功耗特征开始拖累产品形态

### 结论 3：换主控时应按产品方向选型，不应只按“更强”选型
推荐分三类看：

1. 继续快速迭代 MVP
推荐：继续用 ESP32-S3
适用条件：
- 本地规则判断 + 轻量模型
- 主要交互仍是 LED / 震动 / BLE / 小程序
- 需要最快保留现有代码资产

2. 做低功耗可穿戴量产预研
推荐：优先评估 Nordic nRF54H20 或 Ambiq Apollo4 Blue Plus
适用条件：
- 更强调续航、佩戴舒适度、BLE 中心化、边缘传感融合
- 不强依赖 Wi-Fi
- 更接近手环/挂件/医疗健康设备路线

3. 做更强独立语音 / HMI / 本地 AI 交互
推荐：优先评估 NXP i.MX RT1060 级别 crossover MCU
适用条件：
- 想做本地语音控制、更多麦克风、显示、复杂 UI 或更强本地推理
- 接受更高开发复杂度和更重的硬件架构

## 面向 HOLD 的实际建议

### 建议 A：短期不要换主控，先把“独立使用”真正定义清楚
先收敛你们到底要让设备离开手机后独立完成什么：
- 只是判断“平稳/轻度紧张/明显紧张”并启动呼吸引导
- 还是要本地播报、语音交互、自然语言式建议
- 还是要做更完整的连续健康状态画像

如果只是第一类，ESP32-S3 足够。

### 建议 B：优先补一版“脱离手机独立模式”需求文档
建议下一版需求明确以下边界：
- 无手机时设备端要显示/反馈什么
- 设备端判断周期是秒级、分钟级还是事件触发式
- 设备端能容忍的误判率与延迟
- 是否需要本地语音、蜂鸣、屏幕、存储历史
- 目标续航是几小时、几天还是一周

没有这些边界，讨论换 MCU 会很容易失真。

### 建议 C：中期做两条平行预研，而不是立刻整仓迁移
推荐：
- 主线继续保持 ESP32-S3，把算法、交互和传感路线做扎实
- 支线单独开一个“下一代主控预研”分支

支线建议优先级：
1. nRF54H20：如果你们更看重 wearable、低功耗、BLE、传感融合
2. Apollo4 Blue Plus：如果你们更看重超低功耗、健康分析、手环/挂件产品气质
3. i.MX RT1060：如果你们更看重本地语音、复杂 HMI、更强边缘计算

### 建议 D：当前最不建议的做法
- 还没明确“独立使用”定义，就整体迁移主控
- 因为听说某竞品 MCU 更强，就直接换平台
- 在传感和算法尚未收敛前，把大量时间消耗在底层平台迁移上

## 关于当前功耗与存储空间的补充判断

### 1. 180 mA 平均电流意味着什么
180 mA 平均电流对可穿戴设备来说偏高，而且对 XIAO ESP32-S3 这一级平台而言，这通常不是“低功耗已优化后的结果”，而是系统长期处于高活跃状态。

已查到的公开参考边界：
- Seeed 对 XIAO ESP32-S3 给出的典型板级数据中，基础运行约为 5V@19 mA 或 3.8V@22 mA
- 同页给出的典型值里，Wi-Fi active 大约在 81 到 100 mA 量级，BLE active 大约在 85 到 101 mA 量级
- 板级 light-sleep 典型值约为 2 到 2.45 mA，deep sleep 典型值约为 14 到 33.51 uA
- ESP-IDF 官方说明，ESP32-S3 可以通过 DFS、Auto Light-sleep、Deep-sleep 明显降低系统功耗，但前提是任务调度、无线活动和外设唤醒都经过专门设计

因此，180 mA 更像是下面几项叠加后的结果：
- CPU 长时间跑满或较高主频运行
- BLE 持续连接并高频通知，甚至伴随 Wi-Fi
- 传感器持续采样且没有做 duty cycle
- LED、马达、加热或其它反馈器件占用显著电流
- 主循环几乎没有真正进入 idle/light sleep

### 2. 功耗理论上能做到多低
这个问题必须分三层回答，不能只看芯片宣传值。

第一层，芯片或开发板空闲低功耗边界：
- 仅看 XIAO ESP32-S3 板级公开数据，light-sleep 可以到约 2 mA 量级，deep sleep 可以到几十 uA
- 这是“绝大部分时间在睡”，而不是“持续检测并实时交互”

第二层，你们产品这种持续工作形态的可实现区间：
- 如果保持连续多传感采样、持续 BLE 连接、实时判断，并且还带灯光/震动/热反馈，那么平均功耗很难接近毫安级睡眠数据
- 如果去掉 Wi-Fi，控制 BLE 通知频率，降低 CPU 主频，采用 DFS 和 auto light-sleep，并把传感和算法改成分时运行，工程上更合理的目标通常是先从 180 mA 压到 20 到 60 mA 这一档
- 如果允许事件触发式工作，而不是全时高频连续运行，例如采样一小段、处理一小段、缓存结果后进入 light-sleep，那么进一步压到 5 到 20 mA 平均电流才有现实意义

第三层，什么情况下做不到很低：
- 只要加热、强震动、长亮 LED、持续无线传输同时存在，平均功耗就很难低
- 如果产品要求“持续贴身检测 + 持续连接手机 + 持续实时显示/输出 + 高频算法处理”，那么 ESP32-S3 这类平台即使优化，也不会变成超低功耗手环水平

结论上可以直接说：
- 从 180 mA 压到几十 mA，有现实可能
- 想在当前工作形态下直接压到几 mA 以内，基本不现实
- 想稳定做到超低功耗 wearable 水平，往往需要重新设计工作占空比、无线策略，甚至更换到更偏低功耗 wearable 的 SoC 路线

### 3. 空间不够，能不能靠加内存卡解决
可以解决一部分，但不能把“内存卡”当成“运行内存”。

必须区分两类空间：

1. 存储空间不够
这指的是：
- 模型文件放不下
- 历史记录、原始数据、日志、数据库文件放不下
- 固件分区太紧张

这种情况，加 microSD 或外部 flash 是有效的。

依据：
- Seeed 官方资料里，XIAO ESP32-S3 Sense 路线支持 SD card slot，支持 32 GB FAT
- ESP-IDF 官方明确支持 FatFS 和 SDMMC 访问 SD 卡
- 官方文件系统指南也明确把 FatFS 作为常规数据存储、日志、文件目录操作的推荐方案

因此：
- 模型文件、历史波形、日志、离线报告、SQLite 数据文件，这些“冷数据”和“容量型数据”可以放到 SD 卡
- 如果你们只是担心本地数据库文件、记录历史或离线包体大小，SD 卡是可行的

2. 运行内存不够
这指的是：
- 推理时 tensor buffer 不够
- 多任务栈、消息队列、缓存不够
- 模型加载后 heap 爆掉
- 连 BLE、传感、算法一起跑时 RAM 紧张

这种情况，SD 卡不能直接解决。

依据：
- ESP-IDF 官方说明，ESP32-S3 的外部 PSRAM可作为运行期扩展 RAM 使用，最多映射到 32 MB 虚拟地址空间
- 但 SD 卡属于外部文件存储，不是运行时 RAM，不能替代 heap
- 官方也明确指出，PSRAM 在 flash cache 被关闭时会不可访问，而且 task stack、DMA、flash 操作路径仍有约束

因此：
- SD 卡适合“存模型文件”和“存数据库文件”
- 真正推理时需要的中间缓存、栈、队列、实时缓冲区，还是要靠内部 RAM 或 PSRAM
- 如果你现在说“想跑模型但是空间不够”，先确认到底是 flash 不够，还是 heap/PSRAM 不够，这两个解法完全不同

### 4. 数据库这件事应怎么理解
数据库也分两类需求：
- 本地少量历史记录、索引、查询
- 高频、大量、连续写入的时序数据

如果只是第一类：
- SQLite 这类嵌入式数据库从原理上适合 IoT 和设备端本地存储
- 但在 ESP32-S3 这类资源受限平台上，若同时还要跑多传感和模型，数据库层最好保持轻量

如果是第二类：
- 不建议把高频原始流全都实时写成复杂数据库事务
- 更实际的方式通常是：原始流分段文件化存储，数据库只存索引、摘要、时间戳、标签和结果

这比“全部数据都进数据库”更稳，也更省功耗。

### 5. 面向你们当前阶段的直接建议
最务实的判断是：
- 如果当前瓶颈是历史数据、日志、模型文件放不下，可以加 SD 卡或转更大 flash 容量版本
- 如果当前瓶颈是推理时 RAM 不够，SD 卡帮不了本质问题，要看 PSRAM 利用率和任务内存布局
- 如果当前平均电流 180 mA 是在持续工作模式下测得，先不要急着换主控，先做一次功耗拆账

建议优先做功耗拆账，至少分出这几项：
- 纯主控空载电流
- BLE 连接但不发高频数据时电流
- 传感器全开时电流
- 震动开启时电流
- 热反馈开启时电流
- Wi-Fi 开启时电流

只有拆出这几个桶，才知道你们是“平台先天不合适”，还是“当前软件工作方式没有做低功耗设计”。

## 推荐的下一步动作
1. 先补一份“脱离手机独立模式”需求文档，明确本地判断、反馈、续航和交互边界
2. 在现有 ESP32-S3 上做一版真正可脱机运行的规则引导闭环，验证用户体验
3. 同时开一个下一代主控预研小任务，只做 1 到 2 颗候选：
   - 低功耗路线：nRF54H20 或 Apollo4 Blue Plus
   - 语音/HMI 路线：i.MX RT1060
4. 只有当 ESP32-S3 在实际独立模式验证中暴露出明确瓶颈，再决定是否迁移主控
